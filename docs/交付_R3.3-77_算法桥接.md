# R3.3-77 模块间算法桥接·网状多维交互联动 — 交付文档

> 范围：在 `services/bridges/` 新建桥接层，把可联动模块之间的"星形裸调用"升级为
> **双向、多跳、事件驱动**的网状算法桥。逐条对照需求文档 3940–3955 行的 7 条验收点。

---

## 一、设计概览

```
                    ┌─────────────── BridgeBus（共享本地消息总线）───────────────┐
                    │  组合 EventBus（深度防环/单轮去重）+ 载荷 schema 校验    │
                    │  + 命名消费方登记 + 总线级指标                             │
                    └───────┬───────────────┬───────────────┬──────────────────┘
                            │               │               │
        ┌─────────── 双向桥（每座：语义转换+约束通道+仲裁钩子+指标）───────────┐
        │                                                                     │
 TaskEngine ←→ AffectionEngine ←→ Pet表现(WS sink)                              │
    │                │                                                          │
    └→ DirectionCompass ←→ script_library ←→ SixLayerProfile                   │
    └→ MemoryService                                                          │
                            │                                                 │
                    ConflictArbiter（主线不损：任务>好感>罗盘>表现微调）          │
```

- **事件驱动、不轮询**：桥只订阅事件；状态变化通过 `publish` 向下一跳传播。
- **服务层纯 Python**：不 import PySide6；桌宠桥通过 `pet_sink` 惰性导入
  `app.pet_ws_server._broadcast`，headless 测试用 `InMemoryPetSink` 捕获事件流。
- **兼容层底线**：`services/event_bus.py` 一个字节都没改；`BridgeBus` 只是**组合**
  它（可注入 service_facade 已有的 bus），存量 `service_facade` / `tests/test_event_bus.py`
  接线全部继续工作。

## 三、7 条验收点逐条对照

### 验收点 1：每联动对有明确输入/输出/语义转换/约束通道
- 每座桥 `translate_in()` 做语义翻译（例：好感总分 → 桌宠情绪枚举；罗盘缺口维度名 → 跟进任务标题）。
- 每座桥 `constrain()` 做约束通道：
  - 任务→好感奖励钳制在 `[0.5, 10]`；
  - 桌宠→好感微反馈钳制在 `[0.1, 1.0]`；
  - 话术风格白名单（温柔/中/幽默/松弛），非法值回落温柔；
  - 空内容/过长内容去噪。

### 验收点 2：≥3 组双向桥 + 多跳（实际做了 5 组）
| 桥 | A 方向（真写） | B 方向（真写） |
|---|---|---|
| ① 任务↔好感 | 任务完成→`affection.add_bonus` 真实加分 | 好感等级→`task_engine.add_custom_task` 下修/推进任务 |
| ② 任务↔罗盘 | 任务/好感→`compass.evaluate` 真实重算三重闸门/漂移/缺口 | 罗盘缺口→`add_custom_task` 对齐任务；漂移→给空间任务 |
| ③ 好感↔桌宠 | 好感总分→桌宠 `emotion` 事件（sink/WS） | 桌宠上行交互→`affection.add_bonus` 微反馈 |
| ④ 记忆↔任务 | 新事实→`add_custom_task` 话题跟进 | 任务完成→`memory.add_conclusion` 打法沉淀 |
| ⑤ 侧写↔话术 | 侧写成熟→`script_library.pick_scripts` 真实挑话术 | 话术使用→`SixLayerProfile.add_evidence` 真实写回 |

**多跳链（事件驱动传播）**：
`TASKS_COMPLETED` →（桥①）`affection.add_bonus` → publish `AFFECTION_LEVEL_UPDATED`
→（桥③）桌宠 `emotion` 事件（sink 可见）+（桥①B）节奏任务真实入 tasks 表
→（桥②）`compass.evaluate` → publish `COMPASS_RECALIBRATED` →（桥⑤）按漂移挑话术。
在 ≥3 个真实模块状态（好感分数、tasks 表、桌宠事件流、记忆表、六层画像）上同时可见。

### 验收点 3：事件驱动
- 全部联动靠 `publish/subscribe`，无轮询、无硬编码定时。
- 事件类型集中在 `events.py`；每个事件在 `PAYLOAD_SCHEMAS` 登记必填载荷 key；
  `BridgeBus.publish` 校验，缺 key 即去噪丢弃并计数。
- 优先复用存量事件常量（`AFFECTION_CHANGED/TASKS_COMPLETED/MEMORY_UPDATED/...`），
  生产环境把 service_facade 的 EventBus 实例注入即可直接挂钩其已发布事件。

### 验收点 4：双向反馈
桥两端都真写：
- 任务影响好感（add_bonus），好感反哺任务节奏（add_custom_task）；
- 桌宠表现反映好感（emotion 事件），桌宠交互回写好感（微反馈 add_bonus）；
- 记忆产任务线索，任务完成沉淀记忆结论。

### 验收点 5：冲突仲裁 / 主线不损
- `ConflictArbiter` 文档化优先级（数字越小越高）：
  `任务线(1) > 好感(2) > 罗盘(3) > 表现微调(4)`。
- 多跳中两源同写 `task_engine.rhythm_hint`：好感桥说"趁势推进"，罗盘桥说"给空间"，
  仲裁结果**确定性**为高优先级"趁势推进"，罗盘一方被压制并计数。
- 主线上限任务结构本身不走仲裁（任务线恒为最高优先级，下游无法覆盖）。

### 验收点 6：可观测
- 每桥记录：events_in / conversions / failures / failure_rate / avg & max latency_ms。
- 总线汇总：去噪事件数、仲裁压制数。
- 排查口径：`conversions=0` = 挂了没连通；`fail_rate` 高 = 连通但报错；
  `events_in>0 但 conversions=0` = 连通没联动（语义去噪了）。

### 验收点 7：不跑偏
全部桥接服务于游戏化 AI 恋爱指导（任务推进/好感经营/方向对齐/话术/记忆/桌宠陪伴），
未加无关功能，未擅自添加伦理/价值/限制。

   +5 奖励只让总分动 ~0.3。这是引擎本身的设计，不是桥的 bug；断言用"单维分数
   变化"而非总分，避免被取均值掩盖。

   同一 EventBus（见第六节）。

   接的是 `SixLayerProfile`（对方面向六层画像）；用户侧心理画像暂无现成落点，
   未强行臆造一个模块。
4. **NPC↔任务桥已补做（打回后）**：见 `relationship_task_bridge.py`，双向链已验证。
5. **桌宠真实 WS 广播已验证（打回后）**：生产态走 `pet_ws_server._broadcast`，
