## 二、`reachable` 的严格口径（2026-10-17 r2 修订，取代 r1 口径）

| 取值 | 含义 | 判定依据 |
|---|---|---|
| `True` | **收到了服务端/边缘的 HTTP 响应**（任何状态码，含 200/401/403/405/429），即**主机可达** | 端点在线、对本网络开放；能否真正调用另看 `need_key`/`need_login`/`note`。★ 匿名被拒（401/403）也属此类 |
| `False` | **没有收到任何 HTTP 响应**：连接超时 / DNS 解析失败 / 连接被拒 / TLS 握手失败 | 只有这一类才能表述为「本机网络不通 / 不可达」 |
| `"unknown"` | 需要 key 或登录态、端点不公开，**匿名请求无法触达判定** | 宁可 unknown，绝不写 True |

- 非 HTTP 通道（如 SSH）按**同口径**以「服务端是否应答」判定（本轮据此把 `hf_ssh` 判为 True）。
- `latency_ms` 只填**真测到**的往返毫秒（未测到填 `None`）。`False` 的条目一律 `latency_ms = None`（没有应答就没有往返可记）。
- 前 8 条中的 pollinations / llm7 / openrouter_free / nvidia_nim 的 `latency_ms` **沿用**其 2026-10-10 / 10-13 原测值（本轮只复测确认仍返回 200，未覆盖原数值）；本轮新测条目取 **2026-10-17 03:28 第 1 次测量**值。

**怎么读**：`Permission denied (publickey,keyboard-interactive)` 是 **SSHD 的应答**，说明 DNS 解析成功 →
TCP 22 连通 → SSH 协议握手完成 → 服务端要求公钥/交互式认证（我们没有凭据）。这与刚才的 403 同类：
**服务端有应答 = 主机可达**，只是**匿名不可用**；exit=255 只是 ssh 的通用失败码，不代表"网络不通"。
（退出码 255 正是上一版把它误读成"无公开 SSH 端点"的原因。）

## 七、遗留与风险

1. **403/405 类「可达但不可用」是本清单最容易读错的地方**：本轮已在 `note` 里逐条显式写明状态码与含义，
   并加了两条测试护栏防回归。**任何人看到 `reachable=True` 都不能推断"能直接调"**——请连 `need_key` / `note` 一起读。
2. **3 条真不可达（False）是本机网络所致**：google_gemini / mistral / huggingface 全是连接超时（国内网络常需代理）。
   换网络或加代理后需**重测**才能改这一栏；`hf_ssh` 反过来是"有应答但缺凭据"。
3. **两个注册表端点已过期**：`models.inference.ai.azure.com`（DNS 已不存在）、
   `api.cohere.ai/compose/v1`（现行 `/v2`）。清单已按现行端点登记并写进 `note`，但**上游注册表
   `gateway/app/providers/registry.py` 未改**（不在本轮允许改动的范围内）。
4. **额度与限速会漂移**：`free_tier_note` 只写形态与来源，具体数值以官方为准，不要当 SLA。
5. **全部 10 条未接入**：`code_path` 均为「未接入（仅登记）」。要真正接入需在 `services/free_model_router.py`
   里加候选 provider 并做 key 配置，届时 priority 应按实测成功率重排。
6. **复查建议**：沿用 §4.1 的命令复测，只改 `reachable` / `latency_ms` / `probe` 三处；
   改前先备份，别把"匿名被拒"再写成"网络不通"。
