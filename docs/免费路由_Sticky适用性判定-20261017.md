## 0. 一句话结论

**裁定拆两半（2026-10-17 二次修订后）**：

## 2. 裁定与理由（按路径）

### 2.1 主判定：机制层 **(a) 结构上不适用**（但「因此无缺口」的引申已作废 → 见 §2.1b）

理由（三条，均被实证）：

1. **出站调用形态是"两条字符串"，Sticky 取不到会话键。** 所有调用点都是 `llm.chat(system_prompt, user_prompt)`；`messages` / `multi_turn` 恒为默认 `None` → `_resolve_session_key()` 恒返回空串 → **不建也不命中**（实证 F：`session_key=''`；`free_model_router::FreeModelRouter._resolve_session_key`，2026-10-17 复核 @`:1386`）。Sticky 需要"第一条 `role=user` 消息"才能算 SHA1，"是否多轮"也靠 messages 里的 assistant 历史判定——本产品不产生这个列表。
2. **它要解决的问题在本产品不存在（机制层结论；但「因此产品无缺口」已被推翻，见 §2.1b）。** Sticky 的靶子是"多轮中途换模型 → 上下文格式不兼容 / 设定断裂"（见 `SKILL.md` §5 设计意图）。本产品**每轮把历史整段重放进 system prompt**：`digital_twin.py:739` 的 `【最近聊天记录】{chats_text}`（表 A1–A6 实证非空）、`prompts/chat_analysis.txt` 的 `【聊天记录】{{chat_text}}`（表 B1 实证非空）、`consult_engine.py:494` 的 `之前的对话：`（表 C 实证第 2 轮非空）。历史既然每轮都在 prompt 里，**换模型不丢上下文、也不存在"上下文格式不兼容"**（换模型后仍是同样的字符串 prompt）。
3. **一次性生成型调用更不该粘。** ~~`digital_twin.predict_reaction` 等以 `recent_chats=[]` 触发时（`service_facade.py:4031`/`:4044`/`:4057`）是**互相独立**的一次性工具调用~~ —— **此辩解 2026-10-17 已作废**：那三处实为 `:4101`/`:4114`/`:4127` 的**真数据缺口**（非"设计如此"，已修，见 §2.1b）；`multi_dimension_analysis`（`:1861`）、`tutorial_engine`（`generate_task_direction` `:340`，出站 `:365`）是无对话状态的一次性生成。把它们粘在某个模型上只会白白降低调度弹性（`SKILL.md` §5 硬约束①的本意）。

### 2.1b 「因此无缺口」作废：D5 真数据缺口（**已按最小改动修好**）

- **缺口**：`app/service_facade.py::ServiceFacade.predict_reaction` / `simulate_reply` / `compare_options` 修前一律传 `recent_chats=[]`（初稿引作 `:4024`→`:4031` / `:4037`→`:4044` / `:4050`→`:4057`，**实测真锚点为 def `:4094`/`:4115`/`:4133`、twin 调用 `:4101`/`:4114`/`:4127`**，见 §6）；而同一个 `twin.predict_reaction` 在 `service_facade::_run_analysis`（`:1536`）、`service_facade::_run_background_services`（`:1954`）、`app/background_scheduler.py`（`:343`）都收**真实历史（实测 10 条）**。
- **后果**：这三个入口下 `digital_twin::_build_system_prompt` 的【最近聊天记录】=「（暂无）」，并按 `digital_twin.py:750` 把 `confidence` 上限压到 0.5（历史 <10 条）/ 0.3（<5 条）。
- **可达性（如实）**：v3.0 已删 `@Slot` 桥（`app/application.py:5`、`app/service_facade.py:2`），UI 原生直调 facade；全工程 grep 这三个方法名，`app/` 内**仅命中自身定义、无控件调用点**（`DigitalTwinPanel` 只调 `facade.get_twin_panel`）→ **当前不是用户点得到的活缺陷**，但属「同一能力两条入口行为不一致」的隐藏缺口，任何入口/脚本一调即暴露。
- **修法（最小改动）**：三处不再传 `[]`，改取 `chat_text` 的**上游来源**——`service_facade::ServiceFacade.get_chat_messages(person_id, limit=10)`（即 `app/widgets/main_window.py::_on_load_analysis` 生成 `chat_text` 用的同一个方法，`:1822`→`:1840`），映射为 `[{"direction","content"}]`（`digital_twin::_format_chats` 原生支持的 dict 形态；末 10 条窗口与 `_run_analysis`/后台同口径）。**为何不是逐字照抄 `:1536`/`:1956` 那一行**：那两处的来源是所在方法的入参 `chat_text`，这三个方法**没有该入参**（且明确不许改签名）；`get_chat_messages` 正是 `chat_text` 的上游，属同文件既有方法——未新增依赖、未发明新取数方式。（若评审认为此仍属"另择来源"，回滚点见 §5 备份路径，改动本身仅 3 个 hunk。）

### 2.5 `services/tutorial_engine.py`：(a)

一次性生成（`generate_task_direction` @`:340`，出站 `self.llm.chat` @`:365`），两次调用 prompt 逐字相同、无历史概念（实证 E）→ 不存在"跨调用继续的对话"，Sticky 无从生效。→ (a)。

### 2.6 `services/voice_pipeline.py`：**条件项**——现状非活缺陷；接入真 gateway 即为真缺口

- 事实（实证 D）：`LLMGatewayAdapter.generate_reply`（`:495-503`）以**固定 system prompt + 当前一句话**出站，**不保存任何历史**；两轮 system 逐字相同。也就是说：**若**它被接到真实网关，它就是标准的 (b)——"历史不在 prompt 里、也不传 `messages=`"的多轮路径，多轮体验会断裂。
- 但它**当前没被接到真实网关**：全仓库唯一的生产调用点是 `app/shortcuts.py:157` 的 `svc.get_voice_pipeline()`（**无参**）→ `services/speech_service.py:446` 形参 `llm_gateway` 为 `None` → `:480 llm = StubLLM()`（`voice_pipeline.py:364-381` 固定罐头回复）。**该路径全程不经过 `LLMGateway`**，也就没有模型路由 → Sticky 结构上无从生效。
- **结论**：语音链路当前的问题不是"缺 Sticky/缺历史"，而是"LLM 阶段是桩（`StubLLM`）"——这属于另一件事，不在本次 Sticky 适用性判定范围内。**因此我按边界规则没有改 `voice_pipeline.py`**；一旦有人把真实 gateway 接进语音链路（`speech_service.py:477` 起走 `LLMGatewayAdapter` 分支），它会在同一刻变成 (b)，届时按 §4.4 补历史。

### 2.7 机制侧：(a) 的成因是"调用方没传"，通道本身完好

`llm_gateway.py:227-259` 与 `free_model_router.py:1219-1234` 的 Sticky 接线都在，且行为可复现（实证 F）。**只要有一个真多轮调用点开始传 `multi_turn=True`（或 `messages=`），Sticky 立刻生效**。当前 `routing_snapshot()['sticky_sessions']` 恒为 0 的直接原因就是这一条。
