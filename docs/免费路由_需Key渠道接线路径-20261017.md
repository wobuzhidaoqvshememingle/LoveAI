## 0. 一句话结论（R3.8 更新：hook 已应用，但仍然是**双闸**）

这 10 家渠道**已登记、已备好描述符与自检，并已于 2026-10-17 接进自动路由**
（R3.8：`free_model_router.candidates()` 第 6 条来源，落点与 hunk 原文见 §4）。

**但「填了 key 就生效」仍然不成立 —— 这是刻意的双闸，不是 bug：**

| 闸 | 位置 | 效果 |
|---|---|---|
| **第一道：来源闸** | `candidates()` 第 6 条来源 | 没配 key → 这条渠道**根本不产候选** |
| **第二道：价格门闸** | `candidates()` 出口 `price_gate_verdict` | 配了 key 但**没进白名单** → 判 `default_deny` 剔除 → **依然 0 候选、0 出站** |

为什么第二道闸对这批渠道总是关着：这 10 条**都没有目录抓取器** →
价格证据集（`free_ids` / `paid_ids`）**恒空** → 它们**只会**落到 `default_deny`。

所以「填 key 即接入」是**两步**，缺一不可（可直接抄）：

```
第 1 步：填 key                      第 2 步：登记白名单
llm.free.groq_key=<你的key>          llm.free.trusted_models=groq:*
```

> 另有一处**必需修正**：白名单的 `provider:` 前缀原先只认路由内核的已知 provider，
> **不含**这 10 个新名字 —— 不修的话 `groq:*` 会被 `_parse_trusted_entries` 当成
> **裸 id**，白名单写了也匹配不上任何模型、**静默失效**（无报错）。
> 已随本轮一并修正（落点 `services/free_model_router.py:349`，见 §4.4）。

## 3. 为什么现在还不会自动路由（填了 key 也不会生效）

关键：**`candidates()` 里根本没有产这些渠道候选的代码**。填 key 只会让
`services/free_key_channels.py::channels_with_keys()` 多返回一条，**没有任何消费者**。

### 证据链（逐层看）

1. **登记层**：`services/free_channel_catalog.py::FREE_CHANNEL_CATALOG`（L52）只是「清单/说明书」，字段是描述性的（`id/need_login/need_key/.../code_path/note`），**没有任何执行能力**；它不参与路由。
   - 相关只读筛选函数：`zero_config_only()`（L435）、`free_but_need_key()`（L440）、`reachable_now()`（L445）、`as_dict()`（L450）。

2. **描述符层（本轮新增）**：`services/free_key_channels.py::FREE_KEY_CHANNELS` 同样**只是数据**；`channels_with_keys(config)` 是纯函数，只读 config、**不发请求、也不产候选**。

3. **候选产出层**：`services/free_model_router.py::candidates()`（L798–L868）现有产候选来源**只有 6 条**：

| `builtin_free` | 它们**不在** `BUILTIN_FREE_PROVIDERS` | 不触发 |
| `proven_free` | id 不以 `:free` 结尾；`free_ids` **恒空** | 不触发 |
| `trusted` | 只有用户**显式登记**白名单才触发 | 看配置 |
| `default_deny` | **以上皆非时的落点** | **拒绝** |

**所以：**

- **填了 key、没进白名单 → 依然一个候选都不产（0 候选、0 出站）。**
  这是**刻意的双闸**，不是 bug：第一道闸（来源闸）只认「配了 key」，
  第二道闸（价格门闸）不认「用户插了 key」这件事本身 —— 它只认免费证据或显式白名单。
- **填了 key + 白名单 → 才真正进池并被调用。**

> **这不是后续要修的缺陷，而是 fail-closed 硬闸的设计意图**：
> 「我没有拿到免费证据」**不等于**「它免费」，所以默认拒绝；
> 要放行必须由用户显式背书（白名单），把责任显性化。

### 4.3 `sambanova` 的实测 `pricing` 非 0 —— 为什么不能把「缺证据」当「免费」

`sambanova` 是本批里**唯一**能匿名拿到真实目录的渠道：2026-10-17 匿名
`GET https://api.sambanova.ai/v1/models` 返回 HTTP 200 + 1340 B，含 6 个模型 id，
且**每一个模型的 `pricing` 各项都非 0**（不是免费模型）。

但它在本模块里的归宿仍然是 `default_deny`，原因很具体：

> 因为它**没有目录抓取器**，本模块「**没有拿到付费证据**」，它只靠 `default_deny` 被挡。

也就是说：**它并不是被 `proven_paid` 拦下的，而是被「什么都证明不了」拦下的**。
这恰恰是**不能把「缺证据」当成「免费」来放行的理由** ——
若当初按「反正没证据、先放行」处理，这个实测已证明**收费**的渠道就会混进免费池。

> 一句话：`default_deny` 挡住的不只是「未知的坏东西」，也包括
> 「本可以是好东西、但当前没有任何证据」的东西。要放它进来，
> 必须由用户写白名单显式背书（`llm.free.trusted_models=sambanova:*`），
> 并且**自己承担它可能计费的后果**。

### 4.4 必需修正：白名单的 `provider:` 前缀原先不认这 10 个新名字

本轮应用 hook 时**额外**发现并修正了一处静默失效（不在原计划 diff 里，但不修则 §0 的
「两步」根本走不通）：

- `_TRUSTED_MODEL_PROVIDERS = frozenset(KNOWN_PROVIDERS)`，
  而 `KNOWN_PROVIDERS` 只含路由内核的 10 个名字
  （`ollama / local_bridge / local_scan / custom / desktop / openrouter / nvidia /

- 修正（落点 `services/free_model_router.py:349`）：
  `_TRUSTED_MODEL_PROVIDERS = frozenset(KNOWN_PROVIDERS) | frozenset(PROVIDER_IDS)`
- 回归护栏：`tests/test_free_key_channels.py` 里有 3 个用例专门锁这条

### 4.7 D3 契约修正：`channels_with_keys()` 不再交出「含占位」的地址

**问题（外部验证方 D3 抓到）**：`channels_with_keys()` 的派生字段 `base_url_resolved`
此前在**必填配置缺失**时仍会返回含未替换占位的地址
（如 `https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/v1`）。
虽然 `candidates()` 有二级守卫（`if not base or "{" in base: continue`）兜住、**无出站风险**，
但契约不清：调用方拿到它不该直接用。

**修法（选 A：从源头拦截，而不是只写进文档）**

- `channels_with_keys()` 现在：**必填配置不齐 → `base_url_resolved` 置空串 `""`**；
  地址里若仍残留 `{`（理论上不该发生）也一律置空。缺什么仍照旧放在 `missing_config`（语义未变）。
- 契约（写进 docstring）：**`base_url_resolved` 为 `""` ⇒ 地址不可用，原因看 `missing_config`；
  非空 ⇔ 保证不含 `{`，调用方可直接使用。**
- 底层 `base_url_for()` **语义未变**（缺配置时仍保留占位，便于诊断「地址长什么样」），
  只在 docstring 里标明「它可能返回含占位地址，要拿去发请求请用 `channels_with_keys()`」。
- 为什么选 A 而不是「只写文档」：这条线的整体口径是 fail-closed ——
  与其要求每个调用方都记得自己再判一次，不如让**源头**永远不产出不可用地址；
  `candidates()` 的 `{` 守卫作为纵深保留不动。

**实测证据（同一 config：有 cloudflare key、缺 account_id）**

```text

channels_with_keys -> [('cloudflare_workers_ai', ['account_id'], 'https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/v1')]

# 修正后（本次重跑，同一脚本）
channels_with_keys -> [('cloudflare_workers_ai', ['account_id'], '')]
```

契约已由测试锁住：`tests\test_free_key_channels.py::TestMissingRequiredConfigSkipsChannel::
test_descriptor_never_hands_out_a_placeholder_url`。

## 8.4 自检脚本改走契约（2026-10-17，D-残留修正）

**问题**：`scripts/free_channel_keycheck.py` 里仍有两处**自己拼 URL**，绕过了
`channels_with_keys()` 的 `base_url_resolved` 契约：
① `check_channel()` 原来用 `fkc.base_url_for(...)` 拼地址，并把「缺必填配置」当成**真失败**
（`failed=True` → 退出码 1）；② `anonymous_probe()` 完全不做判据，直接对
`…/accounts/{account_id}/ai/v1/models` 这种**含未替换占位**的地址发 GET。

**修法（只动这个脚本）**：地址的唯一来源改为契约。
- `check_channel(channel, contract_row, …)`：`contract_row` 取自
  `fkc.channels_with_keys(config, include_env=…)`；`base_url_resolved` 为空串
  （或残留 `{`）⇒ 打印 `缺必填配置（account_id）：跳过`、**`failed` 保持 `False`**、
  **不发任何请求**；新增 `skip_reason="missing_config"` 字段供机读。
- `anonymous_probe()`：`missing_config` 非空或地址残留 `{` ⇒ 直接给一行
  `跳过(缺必填配置)` 证据行（`url=''`），**不发请求**。
- 计数与文案同步：`passed` / `attempted` 排除跳过的条目；汇总行**仅在有条目时**追加
  `| 缺必填配置跳过 N`（因此「无 key 的 `--all`」输出与改前逐字一致）；
  `真实连通验证:` 在有跳过、无尝试时明确写「**未发任何请求**」；`--json` 的 `summary`
  新增 `skipped_missing_config`。
- 探测请求本身（端点、超时、掩码、退出码语义）**未改**。
