# 外部开源项目深度调研报告

> **调研日期**：2026-10-09
> **调研范围**：17 个开源项目，覆盖 5 个方向
> **调研方法**：每个项目用 web.fetch 真读 GitHub/HuggingFace README 与核心源码，不凭搜索摘要下结论
> **核心原则**：LoveAI 是「策略引擎 + 人物侧写」，不是陪聊机器人。只搬工程设计点，不搬陪聊功能。

## 〇、LoveAI 主体性红线

在开始前先钉死：LoveAI 的主体是**给用户出策略建议的侧写引擎**——它模拟"对方"是为了预判"你这句话发出去对方怎么想"，不是自己当 AI 陪用户聊天。所有调研结论都受这条红线约束：

- ✅ 可搬：角色卡字段分层、多后端抽象、主动触发机制、VAD 断句、故障转移、记忆分层、杀猪盘特征库
- ❌ 不搬：AI 主动给用户发消息谈恋爱、语音陪聊接电话、绑死微信/QQ 协议层、把 AI 自己的情绪数值当产品核心

## 一、方向1：LLM 路由网关（对标 free_model_router.py）

> **LoveAI 现状**：3 源（OpenRouter :free / NVIDIA NIM / Ollama+本地桥探测），按「可用→历史成功率→TTFT」排序，429/超时/401/403/5xx 同轮切下一个，OpenRouter 公开 API 动态拉目录，TTL 24h 缓存 + 静态目录回退。

### 1.1 9Router

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/decolua/9router |
| Stars | ★ 30,509 / 🍴 5,813 |
| 最近 push | 2026-10-08 |
| 语言 | JavaScript（Next.js）｜ MIT |

**优点**：
1. 三层级 fallback 概念清晰：Tier1 订阅（OAuth）→ Tier2 便宜 API → Tier3 免费，配额耗尽自动下钻
2. RTK Token Saver 的 fail-open 设计：压缩失败/变大就静默回退原文，错误永不 break 请求
3. 实时配额追踪 + reset 倒计时：区分 5 小时滚动/日/周重置窗口
4. Multi-account round-robin：同 provider 挂多个账号轮询
5. 免费源生命周期标注诚实：README 明确写了哪些免费层已停/砍额度

**缺点/坑**：
1. 核心 app 包是 private 的，只能 npm install 用黑盒，路由引擎源码看不到
2. 免费源极度不稳定（Kiro 砍到 50 credits/月，OpenCode Free 随时变）
3. 2435 个 open issues，功能堆得满

**LoveAI 可搬点**：
- 静态目录里给每个免费 provider 加**生命周期字段**：`status: active/deprecated/limited`、`quota_note`、`deprecated_at`
- **配额倒计时感知**：记录每个 provider 的重置窗口，"距重置 < 1h 且配额快满"主动降级
- **预处理 fail-open 原则**：未来路由前加任何 prompt 压缩/去重，出错就用原文

**避坑**：不要尝试读它源码搬逻辑（包 private）；不要把 OAuth 订阅层搬进来。

### 1.2 FreeLLMAPI

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/tashfeenahmed/freellmapi |
| Stars | ★ 32,387 / 🍴 4,495 |
| 最近 push | 2026-10-09 |
| 语言 | TypeScript（Node 20+）｜ MIT |

**优点**：
1. **签名 catalog 自更新**：每天两次拉 Ed25519 签名的 model catalog，验签后应用；用户自己的 enable/disable 永不被覆盖
2. **Per-key 四维速率计数**：按 (platform, model, key) 记录 RPM/RPD/TPM/TPD，主动学 provider 上限，不等 429 才切
3. **Unified models collapse**：同一 model 在多 provider 出现时合并成 entry，组内严格 failover
4. Sticky session 30 分钟 + context handoff note
5. 6 种路由策略 + named profile
6. 定期 key 健康检查 + `X-Routed-Via` response header

**缺点/坑**：
1. 实时 catalog 是付费墙（$19/年），免费版慢 30 天
2. 34 provider / 635 endpoint 对 LoveAI 过重
3. 单用户 local-first，是桌面 app 不是嵌入式模块

**LoveAI 可搬点**：
- **签名 catalog merge 模式升级**：维护自己的 `free_catalog.json`，拉到远程目录后和本地做 diff 合并，**不覆盖用户手动禁用项**
- **四维速率计数**：从 response header（`x-ratelimit-remaining-tokens`）学每个 provider 上限，剩余预算 < 10% 主动降权
- **Unified model collapse**：OpenRouter 和 NVIDIA 都有 llama-3.3-70b 时，目录合并成 logical model，优先同 model 跨 provider failover
- **Key 健康检查**：启动时对已配 key 发最小探活，结果缓存进目录

**避坑**：不要搬 Fusion（多模型 fan-out）；不要搬 prompt compression pipeline；不要照搬 635 endpoint 规模。

### 1.3 OmniRoute

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/diegosouzapw/OmniRoute |
| Stars | ★ 73,815 / 🍴 10,614 |
| 最近 push | 2026-10-07 |
| 语言 | TypeScript ｜ MIT |
| 备注 | 本质是 9Router 的 fork/超集 |

**优点（本方向最有价值）**：
1. **三层独立 resilience**：
   - **Layer 1 Provider 级 Circuit Breaker**：只在 408/5xx 触发（**429 不算熔断**），连续 N 次失败 trip，reset 后 HALF-OPEN 探测
   - **Layer 2 Connection/Key 级 Cooldown**：单个 key 429 时 base cooldown 指数退避，honor `Retry-After`；成功一次就清零；同 provider 其他 sibling key 继续服务
   - **Layer 3 Model 级 Lockout**：单 model 的 429 只锁这个 model，不锁整个 connection
2. **Terminal states 区分**：banned(403)/expired/credits exhausted 是终止态，直接禁用不进 cooldown 循环
3. 路由策略中对 LoveAI 有用的：`reset-aware`（按配额重置时间排序）、`headroom`（选剩余配额最多）、`lkgp`（stick 上次成功 provider）、`cache-optimized`
4. 16 因子 live scoring

**缺点/坑**：
1. 功能严重臃肿：MCP server、A2A、persistent memory、guardrails、TLS stealth、i18n——coding-agent 全家桶
2. 358 provider / 1312 model，规模过大
3. 592 open issues + 大量 fork 魔改
4. README 营销话术重（"~1.62B free tokens/mo"等数字带水分）

**LoveAI 可搬点（优先级最高）**：
- **三层故障分级（最该搬）**：LoveAI 现在把所有错误一视同仁"切下一个"，应改成：
  - 5xx/超时 → provider 级熔断，连续 3 次失败冷却 60s
  - 429 → key/model 级 cooldown，honor `Retry-After`，没有就 30s 指数退避
  - 401/403 → 终止态，标记 key 失效，下次启动再探活
- **LKGP sticky**：记录上一轮成功的 provider/model，下一轮优先打它
- **剩余配额 headroom 因子**：结合 RPM/TPM 上限和已用量
- **成功即清零**：provider 成功一次后清掉所有错误计数

**避坑**：绝对不搬 MCP/A2A/guardrails/memory/compression/TLS stealth/i18n/desktop app；不搬 19 种策略，只搬 lkgp + headroom。

### 1.4 RelayFreeLLM

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/msmarkgu/RelayFreeLLM |
| Stars | ★ 180 / 🍴 22 |
| 最近 push | 2026-08-31 |
| 语言 | Python（FastAPI + httpx）｜ License 未标注 |

**优点**：
1. **启动前连通性自检脚本**：`python -m tests.test_models_availability`，逐个 provider/model 发探测，输出 PASS/FAIL 表格
2. 简单版 circuit breaker：429 → 60s cooldown → 自动重试下一个
3. 7 维 rate-limit 字段全可视化，JSON 热编辑不重启
4. Session affinity via `X-Session-ID` header
5. Image-aware routing：检测 message 里有没有 image_url，自动限制到 vision model
6. 纯 JSON 文件存储，无数据库依赖

**缺点/坑**：
1. 规模太小（180 stars，6-7 个 provider），参考价值 > 直接搬代码
2. 维护节奏放缓
3. 内置 chat UI 和 admin dashboard，是完整 server 不是库
4. Consistent Output Style 注入会污染 system prompt
5. 没有动态目录拉取，provider 硬编码

**LoveAI 可搬点**：
- **启动时全量探活**：LoveAI 启动或 TTL 刷新时，对每个已配置的 (provider, model) 发最小探活，结果写进目录 `healthy: true/false`
- **简单 cooldown 表**：`{provider: cooldown_until_timestamp}` 内存 dict，排序时过滤
- **7 维 rate limit 配置化**：静态目录里给每个 provider 标注已知 RPM/TPM 上限
- **`X-Session-ID` sticky**：同一人物侧写的多轮请求 pin 在同一 model，避免输出风格漂移

**避坑**：不搬 chat UI / dashboard；不搬 Consistent Output Style 注入；不搬它的硬编码 provider 列表（LoveAI 动态拉目录已更强）。

## 二、方向2：实时语音（对标 speech_service.py 缺口）

> **LoveAI 现状**：pyaudio 录 16kHz WAV → 手动停止 → faster-whisper 离线整段转写 → 填微信输入框。缺：流式识别、VAD 自动断句、语义 EoT、TTS 试听。
> **定位**：实时听对方说话 → 实时出策略建议。不是语音陪聊。

### 2.1 livekit-agents

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/livekit/agents |
| Stars | ★ 14.7k / 🍴 3.9k |
| 活跃 | 2026 年发 1.5.0，4153 commits ｜ Apache-2.0 |

**优点**：
1. VAD 选型：内置 `silero.VAD.load()` 插件
2. **Turn detection 五档可选**：MultilingualModel（语义）/ realtime LLM 自带 / `"vad"` / `"stt"` / `"manual"`
3. **barge-in 处理成熟**：`interruption.mode = "vad"|"adaptive"`，adaptive 能区分真打断和 backchannel（"嗯""哦"）；false interruption 自动恢复（2s 内没出实际转写就从断点继续）
4. 管线组合极简：`AgentSession(vad=, stt=, llm=, tts=)` 一行注入，300+ 插件可混插
5. 状态机事件齐全：`user_state_changed` / `agent_state_changed` 可订阅做 UI 指示灯

**缺点/坑**：
1. 强依赖 LiveKit Server / WebRTC（生产模式必须起 media server）
2. 延迟实测 P50 3.598s / P95 4.649s，是四个开源方案里最慢的
3. 语义 turn-detector 中文弱：unfinished 只有 45.3%——对方话没说完时一半概率抢答

**LoveAI 可搬点**：
- **`turn_detection="manual"` 模式对应 LoveAI 现状**：借它的事件模型，把 speech_service 从"录音线程+转写线程"改成显式状态机：`IDLE → LISTENING → END_OF_SPEECH → TRANSCRIBING → FILLED`
- false-interruption 自动恢复参数（如果将来加 TTS 试听）
- adaptive vs vad interruption 二分法：对方的"嗯""啊"语气词不该触发策略重算

**避坑**：不要为了用它的 VAD 就引入 LiveKit Server/WebRTC/Redis；不要用 MultilingualModel 做中文 EoT。

### 2.3 FireRedChat

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/FireRedTeam/FireRedChat |
| Stars | ★ 590 / 🍴 48 |
| 发布 | 2025-09-16 ｜ Apache-2.0 ｜ 论文 arXiv:2509.06502 |

**优点**：
1. 完全自托管零外部 API：LiveKit RTC + Redis + Docker Compose + 自托管 ASR/TTS/LLM
2. **pVAD（个性化 VAD）**：叠加 ECAPA-TDNN 目标说话人 embedding，能把环境里其他人/噪声的误触发压下去
3. **EoT 模块（本方向最有价值）**：170M BERT 分类器，中文 EoT 准确率 **96.0%**、英文 94.9%——同参数规模碾压 LiveKit 的 373M（中文 70.8%）
4. **barge-in 反直觉好细节**：pVAD 只用来做主说话人时间戳，**刻意不把去噪后音频喂下游 ASR**，而是用 timestamp 从原始未去噪音频切段（保留副语言线索 + LLM-ASR 本来就抗噪）
5. 延迟 P50 2.341s / P95 3.015s，比 LiveKit 快 1.2s

**缺点/坑**：
1. 重：Docker Compose 一套 5 个服务，桌面单进程是杀鸡用牛刀
2. 只有 11 commits，研究系统 + 模型发布，工程封装薄
3. pVAD 需要目标说话人注册（先录 5 秒注册）——LoveAI 场景对象不固定，跑不起来

**LoveAI 可搬点**：
- **170M BERT EoT 分类器**：faster-whisper 出字后，判断"对方这句说完了没"——输入累计 ASR 文本，输出 stop/continue。比 LiveKit 373M 小一个量级，中文还更准
- **"VAD 只出时间戳、原始音频喂下游"原则**：不要拿 VAD 去噪结果覆盖原始 pyaudio 流

**避坑**：不搬 pVAD（要目标人注册，对象不固定）；不整套 Docker Compose 搬过来。

### 2.4 TEN VAD

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/TEN-framework/ten-vad |
| Stars | ★ 2.3k / 🍴 180 |
| 发布 | 2025-06 开权重，2025-11 支持 WASM/Python/Go/Java |

**优点**：
1. **就是一个 VAD，没有别的**——干净到直接当库 import：`from ten_vad import TenVad`
2. 精度硬刚 Silero：PR 曲线优于 WebRTC VAD 和 Silero VAD，测试集公开可复现
3. 说话→停顿切换快：Silero 对"话间短停顿"有几百毫秒延迟且漏短静默，TEN VAD 几乎瞬时
4. **极轻**：RTF 0.0086-0.057（CPU 上每 10ms 音频 < 0.1ms）；动态库 306KB(Linux)/464KB(Windows)，比 Silero ONNX 小 7 倍
5. 16kHz 输入、hop 160/256 samples（10/16ms）——和 LoveAI 现有 pyaudio 16kHz 流天然对齐

**缺点/坑**：
1. **太敏感**（FireRedChat 横评原话）：任何声响都触发，false barge-in rate 高，真实桌面环境（风扇/键盘/微信提示音）会误触发
2. pip 安装对 Windows/Python 版本挑剔
3. 只是 VAD，没有 EoT、没有 ASR、没有状态机

**LoveAI 可搬点**：
- **直接当 silero 替代品**：pyaudio 流式给 TenVad，每 16ms 一帧，process 出概率
- API 极简：`TenVad(hop=256, threshold=0.5)` → `vad.process(audio_frame)` 返回 `{probability, flag, isVoiceDetected}`
- hop=256 (16ms) 正好和 pyaudio chunk 对齐，不用缓冲
- 库体积极小（几百 KB），对桌面打包友好

**避坑**：默认 threshold 0.5 在真实噪声下会误触发，起步调到 0.6-0.7 + `min_speech_ms ≈ 300-500ms` 最短语音门限；不要顺手上 TEN-Agent 全框架。

### 2.5 HuggingFace speech-to-speech

| 项 | 值 |
|---|---|
| 仓库 | https://github.com/huggingface/speech-to-speech |
| Stars | ★ 13.4k / 🍴 1.7k |
| 活跃 | 1437 commits，2026 年仍在加 Parakeet/Nemotron/Qwen3-ASR ｜ Apache-2.0 |

**优点**：
1. **架构就是 LoveAI 要的形状**：四组件各自一个线程，队列串起来——VAD → STT → LLM → TTS。LoveAI 只要前两个半（VAD → STT → 策略 LLM）
2. VAD 默认 Silero VAD v5，参数暴露极细：`thresh` / `min_speech_ms 384` / `min_speech_continuation_ms 192`（续说滞回）/ `min_silence_ms 64` / `short_segment_merge_ms` / `speculative_reopen_ms 800`
3. **Smart Turn v3.2 是最成熟的语义断句**：状态机 `LISTENING / SOFT_ENDED / ANSWERING / CLOSED`；Silero 判断软结束后**不立刻抢答，speculatively 开始 STT/LLM 但留 800ms 重开窗**——如果用户在 800ms 内继续说，之前转写作废、合并新音频重来；不继续就 commit
4. **明确支持 `faster-whisper`**（`pip install speech-to-speech[faster-whisper]`）——和 LoveAI 现有 ASR 完全同源，迁移成本最低
5. 全离线可跑

**缺点/坑**：
1. 默认栈是 Parakeet TDT + Qwen3-TTS，不是 faster-whisper——要显式 `--stt faster-whisper`
2. 依赖重：DeepFilterNet 要求 numpy<2，Pocket TTS 要求 numpy>=2，二者冲突
3. 产品形态是 WebSocket server，不是嵌入现有 Python 进程的库
4. LLM 是延迟大头（LoveAI 不用它的 LLM 部分）

**LoveAI 可搬点（最佳蓝本）**：
- **Smart Turn v3.2 状态机 + 800ms speculative reopen**：
  - 现在：录音 → 按停止 → 整段转写
  - 改成：pyaudio 流式 → Silero VAD v5 每 30ms 一帧 → 检测到静音进 `SOFT_ENDED` → 立刻用 faster-whisper 增量转写已有音频 → 等 800ms，没新语音就 commit 填输入框；有新语音就拼上新 chunk、作废上次不完整转写、重新转
  - 直接消灭"对方顿了一下就把半截话填进输入框"的尴尬
- **VAD 参数默认值直接抄**：`min_speech_ms=384`、`min_silence_ms=64`、`min_speech_continuation_ms=192`
- **三线程队列结构**：VAD 线程、STT 线程、Turn tracker 线程

**避坑**：不整套装下来（不装 Nemo/mlx/ChatTTS/Qwen3-TTS）；不绑死 OpenAI Realtime 协议当唯一接口；不用默认 Parakeet TDT（中文弱）。

### 方向2 落地组合建议

```
pyaudio 16kHz 流
  → TEN VAD（或 Silero v5）每 16ms 出帧
  → 抄 HF speech-to-speech 的 Smart Turn 状态机（LISTENING/SOFT_ENDED/CLOSED + 800ms reopen）
  → 软结束时用现有 faster-whisper 转写
  → 叠加 FireRedChat 的 170M BERT EoT 做"这句话完没完"二次判断
```

## 三、方向3：关系型 AI 记忆 / 漂移检测（对标 memory_service.py + direction_compass.py）

> **LoveAI 现状**：
> - memory_service：SQLite 三类记忆（fact/lesson/conclusion）、七分类、RAG 可选降级 LIKE、遗忘衰减、整合合并

**缺点/坑**：
1. **无主动漂移检测本身**：它假设 AI 自己的身份不漂（靠每轮重注入），不是关系对象的行为漂移
2. 情绪建模依赖外部 Mind MCP 服务，不接就只有关键词扫描
3. 单用户二元配置，无多关系对象概念

**LoveAI 可搬点**：
- **memory_service 加 Scribe 模式**：每 N 轮用小模型写第三人称摘要，把密集对话压缩成 digest，减少检索噪声；日切时写一行 carry note 不冷启动

- **deception_detector 子代理失败安全模式**：后台检测 worker 用"无工具、只读、单轮、交互忙时让路"

**避坑**：不搬"AI 主动 reach out"；不搬 presence orb/hearth 仪表盘；不要假设身份靠"每轮重注入"就够——LoveAI 对象是真实人类，人类会变，需要主动检测变化。

### 3.2 Cognitive-Core

| 项 | 值 |
|---|---|
| 包 | npm `cognitive-core` v0.3.1 |
| Stars | 周下载量 22（非常早期） |
| 发布 | 约 3 个月前 ｜ MIT ｜ TypeScript |

**优点**：
1. **五层记忆架构**：ExperienceMemory（情景，SQLite）/ PlaybookLibrary（程序，SKILL.md）/ KnowledgeBank（语义，Markdown+YAML）/ MetaMemory（元学习）/ ReflexionMemory（反思）
2. **热路径/冷路径分离**：hot path（<200ms，无 LLM）只做轻量存储，重活全 deferred 到"dream"离线 consolidation
3. **Temporal Compression 四级衰减**：Hot（完整）/ Warm（关键步骤）/ Cold（单段摘要）/ Evicted（删除），按 accessScore 分级，带 hysteresis（连续 2 次低于阈值才降级，防抖动）

3. 无公开源码，22 周下载，生产就绪度低
4. 无情绪/关系维度

**LoveAI 可搬点**：
- **memory_service 改四级衰减**：从统一遗忘衰减改成 Hot/Warm/Cold/Evicted 分层——高频访问的保留完整事实，低频压缩成摘要，超期删除。带 hysteresis 防抖
- **hot/dream 分离**：对话时只做轻量存储，重的整合/合并/分析放后台 batch，不阻塞实时响应
- **direction_compass 矛盾检测数值化**：新观察 vs 已有画像算相似度×冲突度，不是靠关键词触发

**避坑**：不搬 Playbook/SKILL.md 文件系统（LoveAI 是 SQLite 原生）；不搬 TaskRouter；这个项目本身没经过大规模验证，搬思路别搬代码。

**优点**：
1. **LangGraph 显式编排智能体流程**：判意图→改写 query→执行搜索→整合→生成，每步模块化可控
2. **多模型按任务分派（YAML 配置）**：聊天/安全审查/embedding/TTS/搜索各用最合适模型
3. **提示词配置外置（prompt.yaml）**：judge/correction/use/entity/summary 六种职责化 prompt 分栏——prompt 即配置、按职责解耦
4. **动态用户画像 + 入库判断**：`judge_message`（"这条信息是否值得长期存进画像？只答是/否"）做记忆闸门

**缺点/坑**：
1. 独立小项目，模型配置一堆占位 key，稳定性无社区背书
2. "动态情感状态"需要先训练 MoE 模型（生成合成数据+训练存 .pth），对快速迭代是过重负担
3. 纯陪聊产品，无侧写/策略语义

**LoveAI 可搬点**：
- **职责化 prompt 外置（prompt.yaml）**：digital_twin 里"判断对方反应/抽取特征/校准人格/对比 A/B"拆成独立配置项，改策略不动代码
- **记忆闸门（judge_message）**：record_feedback 加一道"这条反馈是否真的改变了对对方的判断"的是/否闸门，避免校准数据被噪音稀释
- **按任务分派模型**：便宜模型干判断/抽取，贵模型干关键模拟
- **LangGraph 两阶段**：compare_options / predict_reaction 拆成"先判情境类别→再生成具体反应"

**避坑**：不搬"训练 MoE 情感模型"路线；不为"会说话、有语音、能上网"加 TTS/web search/表情包陪聊功能。

## 七、一句话总结

**LoveAI 的主体性是"策略引擎+人物侧写"，这个不能动。** 外部 17 个项目里真正值得搬的不是功能，是工程设计模式：

- **路由层**：学 OmniRoute 的三层故障分级 + RelayFreeLLM 的启动探活，把"等 429 才切"升级为"主动探活+分层冷却"
- **语音层**：抄 HF speech-to-speech 的 Smart Turn 状态机 + FireRedChat 的 170M 中文 EoT，把"按录音键"升级为"自动断句+实时出字"
- **记忆层**：学 Cognitive-Core 的四级衰减 + Resonant 的日级 digest，把流水账升级为分层压缩
- **侧写层**：抄 SillyTavern 的字段分层+@Depth 深度注入 + 半熟时区的"对方态度向量"，让 predict_reaction 不漂移、有数值
- **反制层**：搬 SoulMatch-Agent 的六种杀猪盘模式枚举，补上专门话术链检测
- **触发层**：学 KouriChat/半熟时区的"判→动两阶段"，让 task_engine 主动弹建议时先判该不该动、动哪种

**坚决不碰**：AI 主动跟用户谈恋爱、语音陪聊接电话、绑死微信/QQ 协议层、把 AI 自己的情绪数值当产品核心。
