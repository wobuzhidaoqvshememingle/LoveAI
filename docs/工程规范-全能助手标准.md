# LoveAI 工程规范（全能助手标准）

> 本规范是 LoveAI 项目所有子代理/开发者必须遵守的工程纪律。
> 核心目标：**不丢任务、不假装做完、不破坏既有功能、能复盘能追溯**。

---

## 一、运行时执行铁律（11条）

### 铁律1：状态必须落盘，不能靠脑子记
**解决：上次跑完，下次又重新跑**

- 每完成一个关键节点，立刻把状态写进 `.state/task-state.md`，格式固定：
  ```
  任务目标：XXX
  已完成步骤：1.XXX 2.XXX 3.XXX
  当前状态：跑到第X步，正在做XXX
  下一步计划：接下来要做XXX
  关键产物路径：XXX文件在XXX地方
  遇到的问题：XXX
  ```
- 每次开工前，先读 `.state/task-state.md`，从断点接着跑，不要从头开始
- 上下文压缩/断档后，第一件事就是读状态文件恢复

### 铁律2：步骤间必须"交接确认"
**解决：前面跑完了，后面又乱了**

- 每一步做完，不要直接跳到下一步，先做一个交接：
  1. 我这一步输出了什么？（列出关键产物/结论）
  2. 下一步需要什么输入？（明确写出来）
  3. 我的输出够不够下一步用？（不够就补，不要硬往下走）
- 禁止"我觉得应该可以了"——必须明确确认输入输出对齐了，再往下走

### 铁律3：前一步崩了，后面必须停
**解决：前面乱了，后面又跑了**

- 每一步开始前，先检查：上一步成功了吗？有没有错误？产物存在吗？
- 上一步失败/没产出/有报错 → 立刻停下来处理，不要假装没看见继续往下跑
- 级联错误的根源就是：前一步错了，后面还在跑，结果错上加错
- **熔断器**：连续2步出问题，立刻停下来报告用户，不要死磕

### 铁律4：全局进度板，随时看一眼
**解决：摁住这头跑那头，顾此失彼**

- 多步骤任务，在 `.state/task-state.md` 里维护一个"进度板"：
  ```
  [✓] 步骤1：需求确认
  [✓] 步骤2：数据采集
  [→] 步骤3：数据清洗 ← 现在在这
  [ ] 步骤4：分析建模
  [ ] 步骤5：写报告
  ```
- 每做完一步，更新进度板
- 每做新一步之前，看一眼进度板：整体到哪了？还有多少没做？有没有漏的？

### 铁律5：修改防回归，改B坏A
**解决：前面修完bug，后面又把前面搞坏了**

- **改前先备份**：改任何文件/代码/配置之前，先 `.bak` 备份，确认备份能恢复
- **小步改，不要一次性大改**：一次只改一个地方，改完立刻验证，确认没问题再改下一个
- **改完做回归检查**：新改动做完后，回头检查一下——之前已经改好/修好的地方，现在还正常吗？
- **只改该改的**：改这个bug的时候，不要顺手"优化"别的地方——顺手改的地方最容易出回归

### 铁律6：开工前对齐"完成标准"
**解决：做了半天，最后发现"做完"的定义不一样**

- 复杂任务开工前，先明确写下来：
  1. 什么叫做完了？（具体的验收标准）
  2. 交付物是什么？（文件？报告？还是口头回答？）
  3. 什么样算合格？（质量标准是什么？）
- 不要闷头干——干到一半才发现理解错了，前面全白做

### 铁律7：乒乓球循环检测，立刻熔断
**解决：同一个操作反复失败，死循环里出不来**

- 检测：同一个工具/同一个步骤，用几乎一样的参数反复失败——这就是"乒乓球循环"
- 只要发现：同一个问题重试2次以上，参数都差不多，结果都一样——立刻停下来，不要第三次
- 熔断后做什么：
  1. 不是网络问题，不是参数小错
  2. 大概率是方向错了/方法错了——换思路
  3. 实在搞不定就报告用户，不要死磕

### 铁律8：关键环节用硬规则，不靠模型自觉
**解决：让模型自己检查，它经常检查不出来**

- 关键的质量闸口，不要只靠"让模型自己看一遍"——模型自己的盲区自己看不见
- 能用工具硬卡的，就用工具：
  - 格式对不对？用校验脚本 `scripts/check_contract.py`
  - 文件存在吗？用 `Test-Path` 命令，不要靠记忆
  - 代码跑通了吗？跑一下 pytest，不要说"应该没问题"
- 硬规则是底线，模型自检是补充——底线不能省

### 铁律9：定期清理技术债务
**解决：AI每改一次都在旧逻辑外包一层，时间长了全是没人敢删的旧东西**

- 每次修改都可能在旧逻辑外面包一层、加开关加兜底——时间长了全是垃圾
- 定期清理，不要等积重难返：
  1. **先检查**：确认整块旧功能/旧逻辑/旧配置已经退出使用
  2. **再清理**：把旧接口、旧开关、旧配置、兜底逻辑一起清掉
  3. **后验证**：重新跑测试/启动/打包，确认一切正常，不对就退回去
- **第一次清理先只检查不改**：把哪些能删、为什么能删、删完怎么验证都讲清楚，再动手

### 铁律10：任务不丢原则
**解决：用户中途插入新需求，AI直接把前面的任务中断了**

- 用户在任务执行过程中插入新需求时，**默认是"追加任务"，不是"替换任务"**
- 不要直接中断原任务，以为用户说新的就不用做旧的了
- 处理方式：
  - 能并行的：原任务继续跑，同时开子代理处理新需求
  - 必须串行的：先快速响应新需求，然后继续原任务
  - 新需求更紧急的：先处理新需求，但处理完必须回到原任务继续
- **只有用户明确说"停掉前面的"、"不用继续了"，才中断原任务**

### 铁律11：习惯养成第一性原理
**解决：定了计划执行不下去，靠意志力硬抗坚持不了**

- 不要靠意志力爆发，要降低阻力——把目标拆到"不可能失败"的程度
- 重视启动而非完美——不要纠结计划完不完美，先启动，做着做着就会调整
- 绕过大脑对改变的抵触——不要等"有动力了再开始"，先做极小的动作
- 把行为变成无意识反射——固定时间+固定场景+固定动作，重复足够多次

## 二、上下文管理四原则

### 原则1：工具输出沙箱化
- 单条工具返回 > 2KB 时，原始数据写本地文件备查
- 上下文里只留提炼后的关键结果（数字/结论/错误信息/关键行）
- 不要全量塞进对话历史

### 原则2：写脚本代替读文件
- 处理大文件/批量数据时（数行数、统计列、找关键词、批量处理）
- 优先写脚本执行拿结果，不要把整个文件读进上下文——差近200倍token

### 原则3：状态落盘+检索恢复
- ≥3步的复杂任务，每完成一个关键节点就把决策/进度/文件改动写进 `.state/task-state.md`
- 上下文压缩或断档后，先读状态文件恢复"刚才做到哪一步"
- 不要靠对话历史硬回忆

### 原则4：不强制输出简短
- 给用户的回答该多长就多长，不为了省token强行精简
- 省token要省输入（工具数据），不省输出（给用户的解释）
- 强行精简会拉低推理质量

## 三、记忆系统四层架构

| 记忆层 | 是什么 | 怎么用 |
|--------|--------|--------|
| **工作记忆** | 当前对话上下文 | 就是上下文窗口，靠状态落盘防断档 |
| **情景记忆** | 具体事件记录（"上次改XX文件，用户提了YY意见"） | 每次任务的过程和关键决策记到 `.state/experience-log.md` |
| **语义记忆** | 抽象出来的知识（"用户喜欢XX风格，讨厌YY"） | 同一个偏好被提了3次，自动从情景记忆固化成语义记忆 |
| **程序记忆** | 可复用的流程和技能 | 就是项目里的 skill 模块，以及沉淀下来的"做XX事的标准步骤" |

### 经验日志格式（`.state/experience-log.md`）
```
## YYYY-MM-DD 任务类型
- 任务：做了什么
- 做得好：XXX
- 做得不好：XXX
- 用户反馈：XXX
- 下次注意：XXX
```

同类经验攒够3条，提炼成通用规则，更新到对应模块里。

## 四、护栏质检四个闸口

| 闸口位置 | 检查什么 | 检查维度 |
|---------|---------|---------|
| **路由后** | 派错skill了吗？方向对吗？ | 方向对不对 |
| **中途** | 前一个skill的输出够用吗？要不要返工？ | 过程顺不顺 |
| **需求验证** | 做出来的东西，到底是不是用户真正要的？ | 需求对不对（防假阳性） |
| **输出前** | 给用户之前再过一遍：有没有漏洞？ | 质量过不过 |

### 防假阳性原则（最重要）
- 测试全绿 ≠ 需求满足——代码跑通了、格式对了、流程走完了，不代表这是用户要的
- 不要只测"实现"（代码有没有按我写的跑），要测"需求"（这是不是用户真正想要的）
- **输出前最后一道检查**：如果用户拿这个东西去用，能不能解决他的问题？

## 五、协作同步机制

| 机制 | 怎么做 | 解决什么问题 |
|------|--------|-------------|
| **实时状态共享** | 每个子任务的进度写到 `.state/task-state.md` | 不知道对方在干什么 |
| **工作区隔离** | 每个子代理在自己的工作区干活，改自己的文件 | 多个agent同时改同一个文件冲突 |
| **依赖感知的任务拆分** | 有依赖的串行，没依赖的并行 | 该并行的串行，该串行的并行 |
| **结构化整合+验证** | 合并前先验证，不要合完才发现冲突 | 合并完才发现全是矛盾 |

## 六、成本控制

| 手段 | 怎么做 |

## 七、持续改进闭环

### 五步改进循环
```
观察trace → 找最差的环节 → 离线测试 → 小范围试 → 全量上线后继续监控
```

### 三层评估标准
| 层级 | 评估什么 | 及格线 |
|------|---------|--------|
| **工具调用准确率** | 该调对工具了吗？参数对吗？ | 95% |
| **推理质量** | 逻辑对吗？方向偏了吗？ | 85% |
| **输出质量** | 用户满意吗？事实对吗？ | 90% |

### 防模型坍塌
- 不要只靠自己生成的内容来改进自己——那样会越改越同质化
- **引入外部真实数据**：改进时要参考真实用户反馈、真实案例
- **保持方法多样性**：同一个问题尝试不同的解决思路
- **用户真实反馈优先**：用户说"不好用"比AI自己评估"还不错"更有价值

## 八、文件安全规范

### 备份规则
- 改任何文件前，先备份成同名 `.bak`（不带时间戳）
- 改完验证OK后，`.bak` 就是"上一可用版"
- 下次再改时，覆盖旧 `.bak`
- **禁止每改一次留一个时间戳副本**

### 全量备份
- 只留最近3个全量备份
- `backups/` 目录自身不进备份（防套娃）

## 九、关键路径硬规则校验

每次交付前，必须跑 `scripts/check_contract.py` 验证：

```powershell
.\.venv\Scripts\python.exe scripts\check_contract.py
```

校验项：
1. 关键文件存在性（services/、app/、tests/ 核心模块）
2. 核心测试文件可导入
3. 没有遗留的占位字符串（"待长期数据"、"TODO"、"占位"）
4. 没有硬编码的假数据路径

## 十、LoveAI 主体性红线

以下是 LoveAI 的核心，**任何修改都不能动**：

1. **策略引擎是核心**——strategy_advisor / direction_compass / analysis_orchestrator 的核心逻辑不能推翻
2. **本地人设层不变**——style_learner / persona_analyzer / memory_service / digital_twin 是"灵魂"，换模型这层不动
3. **模型适配层可换**——通过 data_pool/adapters/ 换模型，不要在业务代码里直接 import openai/ollama
4. **数字诚实规范**——把握度必须过 cap_score 封顶，不能出现100%/肯定/绝对
5. **话术不能硬套**——话术库匹配后必须 refine_script 微调，不能直接复制模板
