## 二、关键排查：LLM 为什么全层级接不上（数字分身只回"嗯/哦"）

这是本轮最重要的诊断，实测逐层定位（非推测）：

| 层 | 实测现状 | 结论 |
|---|---|---|
| L3 云端 | `llm.cloud.api_key` 空，全仓+env 无任何 key | 正常降级 |
| free/ollama | ollama 服务**没起**；且默认探测模型名 `qwen2.5:7b`/`llama3.1:8b` 本机根本没有 → 404 | **根因** |
| L2 | ollama 已装但没 serve；torch/llama_cpp 在 Python 3.14 无 wheel、无编译器装不了 | 起服务即通 |
| L1 onnx | 文件/引擎都在，但实测中文生成复读乱码（"感澍慰"） | 必须保持拒中文 |

**修复后真能跑的路**：
1. 启动 `ollama serve`，本机已有 `loveai-qwen05b:latest`(491MB) / `loveai-qwen15b:latest`(1.1GB)。
2. `free_model_router.py` 默认模型名改为实际存在的两个，并新增 `_discover_local_ollama_models()`：先 GET `/api/tags` 拿本机真实模型列表，按 配置 > 实探(小快优先) > 默认名 排序，以后改名不再 404。
3. `llm_gateway.py` 的 l1 链由 `["l1"]` 改为 `["l1","l2"]`：短消息被判 l1、L1 拒中文后落到 L2(ollama Qwen) 真回复，不再卡死在统计兜底。
4. 清理 config.json 被 PowerShell 写入带入的 UTF-8 BOM（否则 ConfigService 解析失败回退默认）。

实测：free 渠道正确选中 `loveai-qwen05b`，拿到真实中文回复（如"在啊，有什么可以帮助你的吗？"）。

## 四、遗留 / 需用户处理
1. **ollama 需常驻**：本轮的 `ollama serve` 是手动起的，重启电脑后要保证 ollama 自启（或开机自启），否则数字分身会再次掉回统计兜底。
2. **要真·云端高质量输出需配 Key**：DeepSeek/豆包主力链代码已就位，但 `llm.l3.deepseek.api_key`（或 `llm.deepseek.api_key`）为空；配上 DeepSeek Key 后复杂推理自动走便宜强模型，月成本可压到 10-20 元区间。
3. **R3.3-14 livekit**：全双工管线骨架与 barge-in 已就绪，但 livekit 本体未安装（离线环境），装上后替换各阶段类即可启用。
4. **本地小模型能力上限**：0.5b 中文指令遵循较弱，1.5b 较慢；这是硬件/模型尺寸决定的，代码侧已接通，质量上限需靠配云端 Key 突破。
5. `models_local/` 下 gguf 走 torch 路线在 Python 3.14 暂不可用（无 wheel），当前统一走 ollama 加载，不影响功能。
