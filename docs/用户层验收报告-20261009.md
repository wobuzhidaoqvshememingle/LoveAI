## 三、需求缺口验收

### 缺口 1：1.5B 人设区分度 —— **部分修**

**结论**：离线规则兜底层有人设差异化，LLM 在线层没有。BPD/NPD 在生产代码里零专属 prompt。

**证据**：

1. `prompts/digital_twin.txt` 只有 424 字节，是**单一模板**，占位符 `{{soul}}/{{personality}}/{{affection}}/{{recent_chats}}/{{feedback}}/{{question}}`，无任何按人设分支的 if/else。
2. `services/digital_twin.py:560-574` `_build_system_prompt()`：把 `self.soul` 文本原样塞进 system prompt，**不按依恋类型追加行为指令**。
3. `self.soul` 的来源 `_soul_from_profile()` (L190-209) 只是把画像事实列成 bullet：`依恋类型：avoid / 冲突模式：xxx / 沟通风格：xxx`——是**事实摘要**，不是行为规则。模型拿到"她是回避型"这几个字，但没拿到"回避型被追就躲、要空间、讨厌逼确认"这种行为指令。
4. 真正按人设差异化的代码在 `_persona_consistent_fallback()` (L455-474)：hardcode 了 avoid/anxious/secure 三套回复银行（6 场景 × 3 类型 = 18 条模板句）。但这个函数**只在 LLM 不可用/输出解析失败时**才被调用（见 L689 `_rule_fallback_reaction`）。
5. grep `BPD|NPD|边缘型|自恋型|borderline|narcissist` 全仓 293 处命中，**生产 services/ 目录下零命中**（全在 `tools/bpd_verification_test.py`、`tests/`、`knowledge/sensitive-word-scanner.py`、`verify_v3.py`）。也就是说 BPD/NPD 是测试脚本里造数据用的标签，运行时数字分身不区分 BPD/NPD。

**要改成什么样才算修好**：
在 `_build_system_prompt()` 里按 `personality.attachment_style` 追加一段**行为规则块**，例如：
- avoid："她是回避型依恋：被频繁追问/逼确认时会后撤、回消息变慢、用'哦/嗯'结束话题；预测时不要假设她会热情主动，她的'我一个人也挺好'通常是真的想静一静，不是试探。"
- anxious："她是焦虑型依恋：你不秒回她会脑补'你不在乎我了'；冲突后她要的是你先表态安抚，不是讲道理；'那你先忙'在她耳朵里等于'你不重要'。"
- fearful："她是恐惧型：既渴望亲密又害怕被抛弃，典型推拉——你靠近她退、你退她追；不要被她的忽冷忽热带跑节奏。"
BPD/NPD 同理：在 `persona_profile.json` 里若识别到 `cluster_b: borderline` 或 `narcissistic` 标签，追加对应行为规则。

### 缺口 2：predict_reaction 视角混淆 —— **部分修**（存在人称不一致）

**结论**：system prompt 用第二人称（"你=她"），user prompt 却切回第三人称（"她会怎么反应"），主语在同一次 LLM 调用里跳了一次，1.5B 小模型容易混乱。

**证据**：

- `services/digital_twin.py:561` system prompt 开头：
  > "你现在要扮演下面这个人，用**她**的思维方式和说话习惯来回答。"
- `services/digital_twin.py:666-674` predict_reaction 的 user prompt：
  > "如果我对**她**说/做：{user_action}\n\n请用**她**的视角回答：\n"
  > "1. **她**的第一情绪反应是什么？(emotion)\n"
  > "2. **她**内心真实想法是什么？(inner_thought)\n"
  > "3. **她**大概率会怎么回复？(possible_replies)\n"
  > "4. **她**会采取什么后续行动？(action)\n"
- 对比同文件 `compare_options` (L840-851) 写的是：
  > "作为**她**，**你**分别会怎么反应？"——第二人称一致，无此问题。
- `app/service_facade.py:3690-3701` facade 层只是透传，没做主语校正。

也就是说：system 让模型"你是她"，user 却让模型"分析她"。模型要在脑子里做一次"你→她"的代词转换，1.5B 模型在复杂上下文下容易把"我（用户）"的反应和"她"的反应混在一起输出。

**要改成什么样才算修好**：
把 user prompt 统一成第二人称，与 system 一致：
> "如果我对**你**说/做：{user_action}\n\n请以**你的**视角回答：\n"
> "1. **你的**第一情绪反应？(emotion)\n"
> "2. **你**内心真实想法？(inner_thought)\n"
> "3. **你**大概率会怎么回复？(possible_replies)\n"
> "4. **你**会采取什么后续行动？(action)\n"
> "5. **你**对这次预测的置信度 0.0-1.0？(confidence)"

输出 JSON 键名保持英文不变，只是把中文代词从"她/她的"全部换成"你/你的"。

### 缺口 3：LLM 规则落地跑题 —— **部分修**

**结论**：策略矩阵本身是纯规则、确定性 OK；但把规则喂给 LLM 后，**没有任何后处理校验 LLM 是否真的遵守了 forbidden 清单**。规则以"参考信息"形式塞进 prompt，对 1.5B 模型无硬约束力。

**证据**：

1. `services/strategy_advisor.py` 全文 grep `llm.chat|llm.|prompt|openai|completion` → **0 命中**。整个文件是纯 Python 规则矩阵（ATTACHMENT_MATRIX / CONFLICT_MATRIX / LOVE_MATRIX / BOUNDARY_MATRIX 等硬编码字典），`analyze()` (L673) 输入画像、输出 `{recommended: [...], forbidden: [...], style_tips, conflict_approach}`，零 LLM 调用。
2. 真正把策略喂给 LLM 的位置在 `services/consult_engine.py:466-484`：
   ```
   【对方人格画像适配（务必据此调整建议与话术措辞）】
   - 对方依恋类型：{...}
   - 推荐技巧：{rec}
   - 高代价动作（用了会导致什么后果）：{forb}
   ```
   措辞是"务必据此调整"——软约束，不是"严禁出现以下技巧"。
3. 同一 system prompt (L496-525) 还塞了：角色设定 + 当前用户状态 + 知识库 + 对话历史 + 8 条回答要求 + 修复引导导向长段。1.5B 模型上下文注意力有限，"推荐/禁忌"只是其中一块。
4. `consult_engine._quality_gate()` (L549-588) 只做三件事：长度检查 / 绝对化词替换（一定→大概率）/ 是否含建议动词。**完全不扫描输出是否命中 forbidden 技巧关键词**（如"后撤/冷处理/制造稀缺/欲擒故纵/PUA/打压/冷冻"）。
5. `tests/test_strategy_advisor.py` 等测试只验证规则矩阵本身（给定画像→recommended/forbidden 对不对），**没有任何测试 mock LLM 输出后断言"输出里不能出现 forbidden 词"**。
6. `logs/loveai.log` 只有初始化日志，无真实 LLM consult 输出样本可对比。

**要改成什么样才算修好**：
1. 在 `_quality_gate()` 加一条 forbidden 词扫描：把 `strategy_advisor.analyze()` 返回的 forbidden 技巧名（去掉括号注释后）作为关键词列表，扫描 LLM answer 文本；命中则记录 warning 并在回答末尾追加"⚠️ 上述建议中 {X} 与对方依恋类型冲突，慎用"。
2. prompt 里把"推荐/禁忌"块从信息块升级为硬约束块："【硬约束：以下技巧绝对禁止出现在建议中：...（出现即视为输出不合格）】"。
3. 加离线测试：mock LLM 返回一段故意包含 forbidden 词的文本，断言 quality_gate 命中并追加警告。

### 缺口 4：consult 自报概率幻觉 —— **已修（代码层不主动报概率）**

**结论**：consult 接口的返回契约里**根本没有概率字段**，代码不硬编码、不编造任何数字概率。残留风险只在 LLM 自由文本里可能自发冒百分比，但不是"接口自己报"。

**证据**：

1. `services/consult_engine.py:115-122` consult 返回契约：
   ```python
   {"answer": str, "mode": str, "intent": str, "emotion": str,
    "intercepted": bool, "sources": list}
   ```
   **无 probability / confidence / 概率 / likelihood 任何字段**。
2. `services/consult_engine.py:496-525` system prompt 的回答要求里，关于措辞的规定是：
   > "4. 避免绝对化：不要使用'一定/肯定/绝对/必须'等表述，用'大概率/建议/可以考虑'替代。"
   是**软化词替换**，不是要求模型输出数字概率。
3. `_ABSOLUTE_REPLACEMENTS` (L57-62)：`{"一定":"大概率", "肯定":"建议", "绝对":"可以考虑", "必须":"建议"}`——没有把"大概率"反向量化成具体百分比。
4. grep 全 consult 相关代码（`consult_engine.py`、`app/widgets/consult_mini.py`、`app/windows/consult_mini.py`、`services/batch7_group1.py` 的 toy consult stub）：`prob|confidence|概率|可能性|likelihood` → **0 命中**（仅"大概率"这个软化词出现 2 次）。
5. `app/service_facade.py:3907-3916` facade 层只是包 `{ok, data}`，不注入任何概率。
6. `services/batch7_group1.py:38-42` 那个 toy consult stub 也只返回 `{mode, focus, answer}`，无概率。

**残留风险（非阻塞，可选加固）**：LLM 在自由文本回答里可能自发写"她喜欢你的概率是 70%"这种话，代码层不解析也不剥离。若要彻底干净，可在 `_quality_gate` 加一条正则：若 answer 命中 `概率是\s*\d+%|可能性\s*\d+%|有\s*\d+%\s*把握`，剥离该句或替换为定性描述。当前不阻塞验收。
