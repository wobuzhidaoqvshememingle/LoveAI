# LoveAI 联动架构与设计参考资料

> 本文档记录 LoveAI 项目可参考的架构模式、游戏设计、心理学模型，用于持续完善联动标准。
> 更新日期：2026-10-07

---

## 一、架构模式参考

### 1.1 黑板模式（Blackboard Pattern）

**核心三组件**：
- **Blackboard**（共享知识库）：所有模块共享的数据存储，模块之间不直接调用
- **Knowledge Sources**（知识源/专业模块）：独立读写黑板，不知道彼此存在
- **Control Shell**（控制器/调度器）：决定哪个模块在什么时候运行

**经典实现**：
- Unreal Engine Behavior Tree + Blackboard：Blackboard是AI的"工作记忆"，每个Key有明确类型定义，Behavior Tree从Blackboard读取数据做决策
- 多Agent系统：Agent通过黑板共享状态，订阅相关Key的更新

**对LoveAI的启示**：
- 我们的中心数据池（person_state_snapshot）就是Blackboard
- 各服务模块就是Knowledge Sources
- 事件总线（event_bus）就是Control Shell的雏形
- **待完善**：明确的Blackboard Keys定义（类型/范围/更新者/触发条件）、控制器调度逻辑（按需触发而非全量订阅）

### 1.2 GOAP（Goal Oriented Action Planning，目标导向行动规划）

**核心思想**：描述"想要什么"（目标）和"能做什么"（行动），让规划器自动算出步骤。

**三要素**：
- **World State**（世界状态）：一组变量描述当前状态
- **Goals**（目标）：期望达成的状态
- **Actions**（行动）：每个行动有前置条件（preconditions）、效果（effects）、成本（cost）

**规划过程**：从当前世界状态出发，找到一组行动序列，使得执行后达成目标，且总成本最低。

**对LoveAI的启示**：
- 目标："将好感度从40提升到60"、"让对方从回避转为安全"
- 行动：各种心理学技巧任务（共情表达/制造稀缺/渐进暴露等）
- 每个行动有前置条件（比如"对方当前情绪不是愤怒"）、效果（好感度+5/信任+3）、成本（用户难度/时间/风险）
- 规划器自动选择最优行动序列，而不是硬编码任务链
- **适合重构任务系统**：当前任务是硬编码生成，GOAP可以让任务自动规划

### 1.3 Utility AI（效用AI）

**核心思想**：每一步选择效用值最高的可用行动，不需要预设目标或计划。

**特点**：
- 每个行动有一个效用函数（utility function），输入当前状态，输出0-1的分数
- 每轮选择分数最高的行动执行
- 适合探索性、事件驱动、结果不确定的场景

**对LoveAI的启示**：
- 策略选择可以用Utility AI：每个策略（推进/给空间/反制/引导投入）有一个效用函数，输入当前人物状态，输出该策略的适用度
- 比硬编码规则更灵活，能处理复杂的多因素权衡
- 可以和GOAP混合：GOAP做长期规划，Utility做短期行动选择

### 1.4 GOBT（GOAP + Utility + Behavior Tree 混合）

**论文提出的混合架构**：
- GOAP做目标规划
- Utility做行动选择
- Behavior Tree做执行控制

**对LoveAI的启示**：长期目标用GOAP规划，当前策略用Utility选择，具体执行用任务系统（类似BT的序列执行）。

### 1.5 架构演进路径

```
FSM（有限状态机）→ 状态爆炸，连线指数级增长
    ↓
BT（行为树）→ 解决连线爆炸，但仍是预设逻辑
    ↓
GOAP / Utility → 动态决策，自动规划
```

LoveAI当前处于"BT+硬编码规则"阶段，可以向GOAP/Utility演进。

## 二、恋爱游戏设计参考

### 2.1 Persona 5 社群系统（Confidant / Social Link）

**核心机制**：
- **好感度点数**：通过对话选择积累，选择匹配角色人格的选项获得更多
- **属性匹配加成**：持有对应属性的人格面具时，好感度获得1.5倍加成（Matching Arcana Bonus）
- **社群等级**：等级提升解锁对话剧情和技能奖励
- **资源管理**：时间有限，需要权衡培养哪个角色

**对LoveAI的启示**：
- "属性匹配加成"可以借鉴：当用户的沟通风格匹配对方偏好时，好感度增益加倍
- 社群等级解锁技能→我们的阶段推进解锁新策略/新任务类型
- 资源管理→用户的时间/精力/金钱也是有限资源，任务系统应该考虑资源约束

### 2.2 Fire Emblem: Three Houses 支援系统

**核心机制**：
- **支援等级**：C → B → A → S（S=恋爱结局）
- **提升方式**：共同战斗、共餐、喝茶、合唱练习
- **战斗加成**：支援等级越高，相邻单位战斗加成越大——情感绑定直接转化为战术优势
- **慢热剧情**：支援对话逐步揭示角色的内心挣扎、家庭期望、创伤

**对LoveAI的启示**：
- "情感绑定→实际优势"：关系好不仅是数字，应该转化为实际沟通效果（对方更愿意配合/更主动）
- 慢热剧情→人物档案应该逐步揭示，不是一次分析完所有信息
- 多维度提升关系→不只是聊天，共同活动（一起做事）也能提升关系

### 2.3 Decalove 多轴关系系统

**8个独立关系轴**：affection / trust / respect / friendship / romance / familiarity / anger / jealousy

**核心设计**：同一输入在不同状态下效果不同——
- affection 60时，teasing是playful argument（+趣味）
- affection 20时，teasing会cost trust（-信任）

**对LoveAI的启示**：
- 我们的好感度18维可以明确归为几个大轴：Trust（信任）、Attraction（吸引）、Comfort（舒适）、Investment（投入）、Respect（尊重）、Emotional（情绪）
- 每个轴独立变化，同一行为对不同轴的影响不同
- 行为效果取决于当前各轴状态，不是固定值

### 2.4 Koi Days 4轴关系

**4轴**：Friendship（蓝）/ Romance（粉）/ Trust（绿）/ Hostility（红）
- 每轴有FP（0-30主点）+ SP（累积到下一级的子点）
- 社交行动提升Friendship，调情/礼物/浪漫行动提升Romance，情感支持/守承诺/分享秘密提升Trust，失败行动/背叛/忽视提升Hostility

### 2.5 SEELE AI Dating 情感深度系统

**监控维度**：
- Trust levels（信任）：通过诚实和一致性建立
- Attraction metrics（吸引）：浪漫化学反应，独立于友谊
- Comfort zones（舒适区）：角色有边界，影响回应方式
- Relationship milestones（关系里程碑）：从陌生人到伴侣的自然进展

**AI vs 传统**：
- 传统：手动编码触发、固定对话标记、预设反应、硬编码阈值
- AI：动态计算、上下文记忆所有过去对话、AI生成匹配情绪的回应、基于玩家风格的自适应进展

### 2.6 inZOI 高级关系AI

**特点**：
- 忠诚度动态变化：随注意力、近期情绪、社交关系而变
- 被动攻击：冲突不一定是直接的，可以是不回消息/敷衍帮助
- 社交恐惧：角色避免被拒绝、失去地位、尴尬

**对LoveAI的启示**：
- 对方的"不回消息"可能是被动攻击，不是简单的忙
- 忠诚度/承诺度应该是动态变量，不是固定属性
- 应该建模对方的"社交恐惧"——回避型不回消息可能是害怕冲突

## 三、心理学模型参考

### 3.1 OCEAN大五人格 + 依恋理论映射

**研究发现**：
- 依恋焦虑与神经质(N)相关性 r=.52（最强关联），尤其是焦虑、抑郁、脆弱性维度
- 依恋回避与宜人性(A)负相关，与外向性(E)的热情维度负相关

**依恋类型的OCEAN画像**：
| 依恋类型 | N(神经质) | A(宜人性) | E(外向性) | 特征 |
|---------|----------|----------|----------|------|
| 安全型 | 低焦虑(N1) | 中等信任(A1) | 中等热情(E1) | 不极端，各维度在功能范围 |
| 焦虑型 | 高焦虑(N1) | 高信任(A1) | 高热情 | 害怕被抛弃，过度寻求确认 |
| 回避型 | 中等 | 低信任 | 低热情 | 情感疏离，回避亲密 |
| 恐惧型 | 高焦虑 | 低信任 | 低热情 | 渴望亲密又害怕受伤 |

**对LoveAI的启示**：
- 人格判断和依恋判断应该互相验证，不是独立的
- 可以从OCEAN维度反推依恋倾向，也可以从依恋倾向补充OCEAN画像
- 当前personality_strategy应该整合OCEAN和依恋，而不是分开处理

### 3.2 Triangular Theory of Love（爱情三角理论）

**三维**：
- Intimacy（亲密）：温暖、理解、沟通、支持
- Passion（激情）：浪漫、身体吸引、情感高潮
- Commitment（承诺）：决定维持关系、长期投入

**组合类型**：
- 只有亲密=喜欢（友谊）
- 只有激情=迷恋
- 只有承诺=空洞之爱
- 亲密+激情=浪漫之爱
- 亲密+承诺=伴侣之爱
- 激情+承诺=愚昧之爱
- 三者都有=圆满之爱

**对LoveAI的启示**：
- 好感度系统可以按这三维分解，当前关系缺哪一维就针对性提升
- 不同阶段重点不同：初识→激情，暧昧→亲密，稳定→承诺
- 攻略目标应该明确是提升哪一维

### 3.3 PAD情感模型

**三维**：
- Pleasure（愉悦）：情绪的正负向
- Arousal（唤醒）：情绪的激活程度（平静→激动）
- Dominance（支配）：情绪的控制感（被控制→在控制）

**对LoveAI的启示**：
- 情感分析不只是"开心/生气"，应该是三维空间中的点
- 同样是"愤怒"，高唤醒高支配=攻击型愤怒，高唤醒低支配=焦虑型愤怒
- 策略应该根据PAD三维调整，不只是情绪标签

### 3.4 IPC（人际环状模型）

**两轴**：
- Agency（能动性/支配）：从服从到支配
- Communion（交往性/亲和）：从冷漠到热情

**对LoveAI的启示**：
- 对方的沟通行为可以映射到IPC空间，判断当前是在"支配-亲和"的哪个位置
- 策略目标可以是引导对方向某个象限移动（比如从"冷漠-支配"移到"热情-平等"）

## 四、对LoveAI的改进优先级

### 高优先级（架构层面）

1. **Blackboard Keys标准化**：中心池每个字段明确定义类型、范围、更新者、触发条件
2. **控制器调度逻辑**：事件总线按需触发，不是全量订阅
3. **GOAP任务规划**：任务系统从硬编码改为目标导向自动规划

### 中优先级（功能层面）

4. **多轴关系系统明确化**：好感度18维归为Trust/Attraction/Comfort/Investment/Respect/Emotional六轴
5. **同一行为不同状态效果不同**：借鉴Decalove，行为效果取决于当前各轴状态
6. **Utility AI策略选择**：策略选择用效用函数评分，替代硬编码规则

### 低优先级（增强层面）

7. **OCEAN+依恋整合**：人格和依恋互相验证
8. **爱情三角理论**：好感度按亲密/激情/承诺三维分解
9. **PAD情感模型**：情感分析三维化
10. **资源约束**：任务系统考虑用户的时间/精力/金钱约束

## 六、从全能助手Skill提取的可借鉴点

### 6.1 Orchestrator两阶段模式

**路由规划→汇总组装**：
- 第一阶段：语义匹配候选模块 → 选哪些、什么顺序、并行还是串行
- 第二阶段：收集各模块结果，整合成最终输出，过质检后给用户

**对LoveAI的启示**：analysis_orchestrator可以更明确地分两阶段——先规划（这次分析需要哪些模块、什么顺序），再执行汇总。当前是硬编码的调用链，可以改为动态规划。

### 6.2 流水线分工

**七条流水线**：内容生产/数据决策/软件开发/知识蒸馏/健康管理/情感法律事务/任务总调度

**对LoveAI的启示**：模块可以按流水线组织：
- **感知流水线**：微信消息→情感分析→言外之意→人格判断
- **决策流水线**：策略选择→任务规划→数字分身预测
- **执行流水线**：回复生成→填入微信→效果跟踪
- **记忆流水线**：记忆提取→画像更新→中心池同步

### 6.3 护栏质检三个闸口

| 闸口位置 | 检查什么 |
|---------|---------|
| 路由后 | 模块选对了吗？方向对吗？ |
| 中途 | 前一个模块的输出够用吗？要不要返工？ |
| 输出前 | 回复符合策略吗？有没有漏洞？ |

**对LoveAI的启示**：在分析流程中加三个质检点——模块选择后检查是否匹配场景、分析中途检查数据是否充分、回复生成后检查是否符合策略方向和用户说话习惯。

### 6.4 模块组合四模式

| 模式 | 结构 | LoveAI应用 |
|------|------|-----------|
| 顺序 | A→B→C | 情感→策略→任务（有严格依赖） |
| 并行 | A和B同时跑，最后汇总 | 财务分析+损失厌恶+记忆提取（互不依赖） |
| 循环 | 执行→审核→不通过→再执行 | 策略→任务→反馈→调策略（需要反复迭代） |
| 兜底 | 主方案失败→自动切备用 | 云端模型失败→本地大模型→小模型→规则 |

### 6.5 分层错误处理

| 错误类型 | 例子 | 处理方式 |
|---------|------|---------|
| 临时错误 | 模型超时/限流 | 自动重试，指数退避，最多3次 |
| 持续错误 | 模块一直失败 | 自动切兜底方案 |
| 级联错误 | 连续5个步骤都出错 | 熔断器：停下来报告 |
| 语义错误 | 分析方向错了 | 不是技术问题，必须停下来重新规划 |

### 6.6 可观测性（Trace/Log/Metric）

| 类别 | 记什么 | 有什么用 |
|------|--------|---------|
| Trace | 每步决策、调了什么模块、结果、下一步 | 出问题能完整回放 |
| Log | 什么时候调了什么、成功失败、花了多久 | 事后排查卡点 |
| Metric | 平均步数、模块成功率、token消耗 | 发现异常趋势 |

**对LoveAI的启示**：每次分析应该记录完整的执行轨迹（调了哪些模块、每个模块的输入输出、花了多久），方便排查"为什么这次分析不对"。

### 6.7 动态重规划

**原则**：计划是临时的，跑一步看一步，发现不对就调整路线。

**对LoveAI的启示**：策略不是一次定终身——执行任务后看对方反馈，如果效果不好就重新规划策略，不要一条道走到黑。当前策略有反馈分支，但可以更主动地重规划。

### 6.8 持续改进闭环

```
观察trace → 找最差的环节 → 离线测试 → 小范围试 → 全量上线后继续监控
```

## 七、游戏AI分层架构参考

### 7.1 Sense-Think-Act循环（感知-思考-行动）

**游戏AI经典架构**：
- **Sense（感知）**：从环境获取信息（视觉/听觉/伤害/队友消息）
- **Think（思考）**：基于感知做决策（目标选择/行为选择/规划）
- **Act（行动）**：执行决策（移动/动画/交互）

**对LoveAI的映射**：
- **Sense**：微信消息输入→情感分析→言外之意→人格判断→关系轴状态
- **Think**：策略选择（Utility AI）→任务规划（GOAP）→数字分身预测
- **Act**：回复生成→填入微信→效果跟踪→反馈回中心池

**关键**：这是一个循环，不是一次性的——行动后的效果（对方回复）又成为新的感知输入。

### 7.2 三层AI架构（战略层/决策层/执行层）

| 层级 | 游戏AI | LoveAI映射 |
|------|--------|-----------|
| 战略层 | 小队/群体策略 | 长期关系规划（阶段目标/攻略方向/关系健康度） |
| 决策层 | 单个角色决策 | 当前策略选择/任务规划/数字分身预测 |
| 执行层 | 移动/动画 | 具体回复生成/填入微信/单步操作 |

**对LoveAI的启示**：当前缺少明确的"战略层"——只有当前策略（决策层）和具体回复（执行层），缺少"这段关系的长期目标是什么、当前阶段的攻略重点是什么"的战略规划。可以加一个relationship_strategist模块，负责长期方向。

### 7.3 意图-任务-行动三层级

**兵棋游戏架构**：
- **意图层**：作战意图（用FSM建模，调整策略）
- **任务层**：任务分配（用联盟博弈，促成协同）
- **行动层**：行动控制（用行为树，根据态势精准控制）

**对LoveAI的映射**：
- **意图层**：关系目标（提升好感/修复信任/引导投入/反制操控）
- **任务层**：具体任务分配（GOAP规划的任务序列）
- **行动层**：每步怎么做（回复话术/时机选择/表达方式）

### 7.4 HTN（分层任务网络）

**比GOAP更适合复杂任务分解**：
- GOAP：从目标反向搜索行动序列
- HTN：将复杂任务递归分解为子任务，直到可执行的原始行动
- 优势：可以表达"先做A再做B"这类时序约束，更适合有阶段的任务

**对LoveAI的启示**：恋爱攻略有明显的阶段（初识→暧昧→热恋→稳定），HTN比GOAP更适合表达"先建立信任，再推进亲密，最后巩固承诺"这类分层任务。可以考虑GOAP+HTN混合。

## 八、多Agent协调模式参考

### 8.1 Contract Net Protocol（合同网协议）

**任务招标-投标-中标模式**：
- Manager广播任务公告（Call for Proposals）
- 可用的Contractor提交投标（能力评分/可用性/成本）
- Manager评估投标，将任务授予最合适的Contractor

**对LoveAI的启示**：当多个策略模块都能处理当前场景时，可以用招标模式——每个策略模块提交"我处理这个场景的适用度评分"，选最高的。这比Utility AI更灵活，因为可以动态加入新策略模块。

### 8.2 Event Sourcing（事件溯源）

**所有状态变化都记录为不可变事件**：
- 状态不是直接修改，而是追加事件
- 当前状态=所有事件的折叠（fold）结果
- 可以回放任意时间点的状态
- 可以审计所有变化

**对LoveAI的启示**：好感度/关系轴/人物画像的变化可以用事件溯源记录——"2026-10-07 14:30，对方说'想你了'，好感度+3，来源=情感分析"。这样可以回溯"为什么好感度是现在这个值"，也可以发现异常变化。

### 8.3 Supervision Tree（监督树）

**带防护能力的层级监督**：
- 每个模块有上级监督者
- 模块崩溃时，监督者决定重启/跳过/降级
- 故障隔离：一个模块挂了不影响其他模块

**对LoveAI的启示**：当前模块是平级调用，一个模块异常可能导致整个分析失败。可以加监督层——数字分身预测失败不影响回复生成，财务分析失败不影响策略选择。

## 九、情感计算参考

### 9.1 情绪动力学

**情绪不是静态的，有动态变化**：
- **衰减**：情绪随时间自然衰减（愤怒不会一直持续）
- **累积**：同类情绪事件会累积（多次被忽视→愤怒升级）
- **传染**：一方的情绪会影响另一方（你焦虑→对方也焦虑）
- **触发阈值**：情绪积累到阈值才会爆发

**对LoveAI的启示**：当前情感分析是单条消息的静态判断，应该加情绪动力学——对方的情绪有衰减曲线，多次负面事件会累积，你的情绪表达会影响对方。可以加emotion_dynamics模块。

### 9.2 情感同步（Emotional Synchrony）

**关系中的情绪会互相校准**：
- 长期相处的伴侣情绪模式会趋同
- 一方情绪调节能力差会拖累另一方
- 情感同步度高=关系满意度高

**对LoveAI的启示**：数字分身预测对方反应时，应该考虑双方的情感同步度——如果用户习惯焦虑表达，对方也会逐渐变得焦虑。策略目标之一是提升情感同步质量。

### 9.3 情绪调节策略分类

**Gross情绪调节过程模型**：
1. 情境选择（回避/接近）
2. 情境修正（改变环境）
3. 注意力分配（关注/忽视）
4. 认知重评（换个角度看）
5. 反应抑制（压住情绪）

**对LoveAI的启示**：给用户的策略建议可以对应这5种调节策略——不是只有"怎么说"，还有"要不要说""什么时候说""关注什么""怎么理解对方的话"。

### 第四批：架构增强（新增）
