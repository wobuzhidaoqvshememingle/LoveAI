## 二、六条跨项目共性工程纪律（比单个算法更值钱）

1. **规则/词典负责可复现的分，LLM 只负责写人话总结**（DSM 的命根子，也是它不幻觉的原因）。LoveAI 凡是要"敢下结论"的分，都别让 LLM 直接打分。
2. **阈值全是别人拍的脑袋，必须用 LoveAI 自己的对话数据重标定**。AIta 的 `<8 字`、PsyDI 的 clamp、UncommonRoute 的特征权重，直接搬过来在中文关系场景都会偏。
3. **fail-closed**：任何"AI 裁决"解析失败/越界，一律 drop/hold，绝不"宁可信其有"（DSM 两阶段裁决、PsyDI 停止条件都该这么改）。
4. **自他者遮蔽是关系分析的命门**：不剥掉"他说/引语"，就会把对方的话算成用户自己的特质（DSM 的 `mask_non_self_spans` 必须搬）。
5. **会话级"只升不降"**：一次会话里难度档位只升不降、30min TTL、连续三次相同请求才升级（UncommonRoute），能解决来回切模型的跳戏和浪费。
6. **选型先认我们自己的栈**：前端是原生 HTML/JS 且已 vendored three.min.js → 直接排除 react-force-graph，用 UMD 版 3d-force-graph；NRD 用 2D Canvas 伪 3D 都能交付，证明我们不必上重型 WebGL 框架。

## 四层各自的真实实现

### 第 0 层公共底座：统一注入管道 `setExtensionPrompt`

四层不是各写各的，全部走同一个函数，靠两个轴控制：**position（插到 prompt 哪个位置）+ depth（插到离最后一条消息多远）**。扩展 tag 前缀数字决定先后：

```js
// 实际出现的 tag（来自源码常量）
const MODULE_NAME = '1_memory';        // 摘要层
export const EXTENSION_PROMPT_TAG = '3_vectors';            // 向量召回层
export const EXTENSION_PROMPT_TAG_DB = '4_vectors_data_bank'; // 资料库层
// 世界书条目注入 depth 由条目自身 extensions.depth 决定，默认 DEFAULT_DEPTH = 4
```

`extension_prompt_types.IN_PROMPT` = 注入到主 prompt 区；`extension_prompt_roles.SYSTEM` = 以 system 角色发。**depth 越大越靠上（越接近角色设定），depth=0 就是紧贴最后一条用户消息**。这是理解四层协同的钥匙。

---

### 第 1 层：角色卡固有设定（main prompt / character definition）

**机制**：角色卡的 description / personality / scenario / creator's note 是**静态常驻块**，永远在上下文顶部，不参与触发逻辑。世界书引擎反过来把它们当作"待扫描文本"的一部分——条目可以配置成只在匹配到角色卡某字段时才激活。

证据在 `newWorldInfoEntryDefinition` 里这一组布尔开关（`public/scripts/world-info.js`）：

```js
matchPersonaDescription:   { default: false },  // 匹配偶娃描述
matchCharacterDescription: { default: false },  // 匹配角色卡 description
matchCharacterPersonality: { default: false }, // 匹配角色卡 personality
matchCharacterDepthPrompt: { default: false },
matchScenario:             { default: false },  // 匹配角色卡 scenario
matchCreatorNotes:         { default: false },  // 匹配 creator note
```

扫描时这些"chat-independent context"被装进 `WIGlobalScanData`，和最近 N 条对话拼一起做关键词匹配（源码注释：*"Chat independent data to be scanned, such as persona and character descriptions"*）。

**关键设计**：角色卡设定本身不"花钱做召回"，它是锚；世界书条目通过上面 6 个 match 开关挂到这个锚上。LoveAI 做关系侧写时，"关系卡点/人设基线"就该常驻这一层。

### 第 2 层：世界书 / World Info（关键词触发 lorebook）

这是 SillyTavern 最成熟、最值得抄的一层。

#### 2.1 条目数据结构（`newWorldInfoEntryDefinition`，真实字段）

```js
export const newWorldInfoEntryDefinition = {
  key:             { default: [] },        // 主关键词数组（keys）
  keysecondary:    { default: [] },        // 副关键词数组（secondary_keys）
  comment:         { default: '' },        // 条目备注（给人看的名字）
  content:         { default: '' },         // 真正注入 prompt 的正文
  constant:        { default: false },     // = true 即"恒显"，无视关键词永远激活
  vectorized:      { default: false },      // 是否参与向量召回（第3层联动）
  selective:       { default: true },       // 是否启用副关键词逻辑
  selectiveLogic:  { default: 0 },        // AND_ANY=0 / NOT_ALL=1 / NOT_ANY=2 / AND_ALL=3
  order:           { default: 100 },       // 插入顺序权重，越大越靠前（sortFn: b.order - a.order）
  position:        { default: 0 },         // before_char / after_char / @depth
  depth:           { default: 4 },         // 注入深度（DEFAULT_DEPTH = 4）
  probability:     { default: 100 },       // 激活后再掷一次概率（100=必中）
  useProbability:  { default: true },
  disable:         { default: false },     // = enabled 取反
  ignoreBudget:    { default: false },     // 无视 token 预算，强制注入
  excludeRecursion:{ default: false },      // 递归扫描时不再把它的正文当扫描源
  preventRecursion:{ default: false },     // 这条激活后不触发下一轮递归
  delayUntilRecursion: { default: 0 },     // 延迟到第 N 轮递归才生效（分级触发）
  scanDepth:       { default: null },      // 本条自定义扫描深度，null 用全局
  caseSensitive:   { default: null },      // 覆盖全局大小写
  matchWholeWords: { default: null },
  group / groupOverride / groupWeight: {...}, // 同组互斥/加权
  sticky:          { default: null },       // 时序效应：激活后粘住 N 轮
  cooldown:        { default: null },      // 冷却 N 轮才能再激活
  delay:           { default: null },      // 延迟 N 轮才首次激活
};
```

#### 2.2 评分（`scoreKey`，真实逻辑）

对每个条目，拿扫描窗口里的文本数命中了几个主/副关键词，按逻辑算分：

```js
// 主关键词每命中一个 +1
for (const key of entry.key) if (this.matchKeys(bufferState, key, entry)) primaryScore++;
// 副关键词按 selectiveLogic 组合
case AND_ANY:  return primaryScore + secondaryScore;            // 任一命中即叠加
case AND_ALL:  return secondaryScore === 副关键词总数
               ? primaryScore + secondaryScore : primaryScore; // 全部命中才叠加
```

没有主关键词命中 → 直接 0 分淘汰。`NOT_ALL`/`NOT_ANY` 是"否定触发"（正文里**不**出现某词才激活，适合写"别再提那件事"这类排除条目）。

#### 2.3 token 预算（核心公式）

```js
// checkWorldInfo() 开头
let budget = Math.round(world_info_budget * maxContext / 100) || 1;
// world_info_budget 默认 25（即上下文窗口的 25%），world_info_budget_cap 可硬封顶
if (world_info_budget_cap > 0 && budget > world_info_budget_cap) budget = world_info_budget_cap;
```

激活条目按 order 排序后逐条注入，**每加一条都重算 token，超预算就停**：

```js
if (!entry.ignoreBudget &&
    (textToScanTokens + await getTokenCountAsync(newContent)) >= budget) {
  token_budget_overflowed = true; break;   // 但 ignoreBudget=true 的条目仍可挤进来
}
```

#### 2.4 选择性递归（selective recursion）

激活的条目正文会被**追加进扫描缓冲**，触发下一轮扫描（用新注入的正文里的关键词再去激活别的条目），形成"链式召唤"：

```js
if (world_info_recursive && !token_budget_overflowed && successfulNewEntriesForRecursion.length) {
  nextScanState = scan_state.RECURSION;   // 用本轮激活条目的 content 再扫一轮
}
// 把本轮新激活条目的正文拼进 recurse buffer
const text = successfulNewEntriesForRecursion.map(x => x.content).join('\n');
buffer.addRecurse(text);
```

`delayUntilRecursion` 让条目"等到第 N 轮递归才醒"，实现多跳因果链；`max_recursion_steps` 防止无限递归（与 min_activations 互斥）。

#### 2.5 常驻/可选/恒显三种态

- **恒显（constant=true）**：不过关键词，永远激活，永远占预算（除非预算爆了且非 ignoreBudget）。
- **可选（constant=false）**：走关键词 + 概率 + 预算三道门。
- **sticky/cooldown/delay**：跨轮次的时序状态机（`WorldInfoTimedEffects`），让条目"激活后粘几轮/冷却几轮"，避免高频抖动。

#### 2.6 min activations（保底激活数）

`world_info_min_activations`（默认 0=关）：如果激活条目数不够 N，就**自动扩大扫描深度**（往前翻更多历史消息再扫），直到凑够 N 条或触顶 `world_info_min_activations_depth_max`。

#### 3.3 前端编排（`rearrangeChat`，这是最值得抄的设计）

它不是"把召回内容追加进 prompt"，而是**真的把命中的旧消息从对话数组里抽出来，重插到指定 depth**：

```js

  depth: 2,            // 召回内容插在离最新消息第 2 层
  protect: 5,          // 最近 5 条受保护，绝不参与召回/抽出
  insert: 3,          // 召回 topK=3 条
  query: 2,           // 用最近 2 条消息反向拼查询文本
  score_threshold: 0.25,
  message_chunk_size: 400,
};

async function rearrangeChat(chat, ...) {
  const queryText = await getQueryText(chat, 'chat');   // 最近 query 条消息倒序拼接
  const queryResults = await queryCollection(chatId, queryText, settings.insert);
  const queryHashes = queryResults.hashes;
  const retainMessages = chat.slice(-settings.protect); // 尾巴 5 条不动
  // 命中且不在保护尾巴里的消息 → 收集成 queriedMessages
  // 再从原 chat 数组里 splice 删掉
  for (const message of chat) if (queriedMessages.includes(message)) chat.splice(...);
  // 拼成 "名字: 正文" 块，套 template，插到 depth=2
  const insertedText = getPromptText(queriedMessages);

```

查询文本构造 `getQueryText`：**取最近 `query`(=2) 条消息、倒序、拼一起**当 query（不是拿用户最后一句，而是最近两句的滑动窗口）。

## 四层协同与 token 预算（反推）

一次生成时，SillyTavern 按这个顺序从大到小占用上下文（数字=depth，越大越靠上=越像"设定"）：

```
[depth 高]
  角色卡 description/personality/scenario      ← 第1层 常驻锚，占满顶部
  世界书 @depth 条目（DEFAULT_DEPTH=4）        ← 第2层 按 order 排，预算=maxContext*25%
  摘要 [Summary: ...] @depth=2               ← 第4层 滚动增量摘要
  向量召回 Past events @depth=2               ← 第3层 topK=3，从对话里抽出来插这
  资料库 chunks @depth=4 (SYSTEM)             ← 第3层扩展
[depth 低]
  最近 protect=5 条原始对话（原样保留）        ← 不召回、不压缩
  最新一条用户消息
```

预算分配的真实逻辑：

1. **先算总账** `maxContext`（模型上下文窗口扣掉预留回复）。
2. **世界书独占一块**：`budget = round(25% * maxContext)`，可被 `world_info_budget_cap` 硬封顶。爆预算后非 `ignoreBudget` 条目全停。
3. **摘要层**走"目标词数"自管（默认 200 词 ≈ 几百 token），不抢世界书预算；它靠 `promptInterval=10` 攒够才生成，是**离线异步**压旧对话，把旧消息腾出来。
4. **向量层** `insert=3` 条硬上限 + `score_threshold=0.25`，召回条数少，token 占用可控；`protect=5` 保证最近 5 条原文永远在。
5. **世界书扫描文本**反过来包含第 1 层（角色卡 6 个 match 开关）+ 最近 N 条对话，实现"人设锚 ↔ 动态条目"双向联动。

协同精髓：**常驻层管"不变的基线"，世界书管"按当下剧情激活的知识点"，向量层管"跨剧情但当下相关的往事"，摘要层管"把太久远的事压成一句话"**。四层用同一个 depth 坐标体系叠放。

## 坏设计 / 避坑

1. **向量召回是"硬抽消息"**：`rearrangeChat` 直接 `chat.splice()` 删除原消息，若召回命中把一条**仍在保护窗附近**的消息抽走，会造成上下文断裂；SillyTavern 靠 `protect=5` 硬挡，但这个 magic number 对长对话偏短。LoveAI 别照搬 splice 删除，建议**软召回（注入副本）**而非物理删除，避免历史错位。
2. **score_threshold=0.25 是全局写死的手感值**，不同 embedding 模型（ada-002 vs mxbai vs bge-m3）分数分布差异巨大，0.25 换模型就失灵。LoveAI 必须按自己用的 embedding 模型重新标定阈值，别直接抄数字。
3. **摘要触发门 promptInterval=10 条**对快节奏情感对话太粗（10 条可能跨了好几个情绪转折点），容易把关键冲突压没。LoveAI 建议降到 6~8 条，或加"情绪剧变事件强制触发摘要"。
4. **世界书预算上限 `world_info_budget > 100 就强制重置回 25`**（源码里有这段 `if (world_info_budget > 100) world_info_budget = 25`），是个硬编码怪癖，LoveAI 不要抄这个粗暴重置。
5. **vectra 是纯文件 JSON 索引**，数据量上万条后查询/写入性能一般，且无增量持久化优化。LoveAI 若消息量大，建议直接用 Chroma/SQLite-vss，只抄它的"hash 主键 + score 过滤 + topK"逻辑，不抄存储层。
6. **AGPL v3.0 传染性**：SillyTavern 整仓 AGPL，代码思路/算法可抄，但**不能直接复制其 JS 源码进 LoveAI**（会传染协议）。只搬设计与数据结构，用 Python 重写。

  + tSentiment.score * 0.3
  + dynamics.targetDominance * 20
) / 4;
```

**第三步：关系阶段级联（从上到下，命中即定）**

```js
if (tCount === 0)                     -> "未识别到对方消息"
else if (isStableRelation)            -> "稳定期"（爱称/自报关系，直接覆盖）
else if (warmthScore > 55)            -> "升温阶段"（互动积极/有亲密表达）
else if (avgLength>12 || followUps>0) -> "互相了解上升期"
else if (avgLength < 6)               -> "礼貌回应阶段"
else                                  -> "相互试探"（兜底）
```

**依恋类型级联（阈值全部拍死在代码里）**

```js
if (tIntimacy.score>50 && tAvoidance.score<30) -> 安全型
else if (tAvoidance.score > 45)                 -> 回避型
else if (tIntimacy.score>40 && tSentiment<40)   -> 焦虑型
else                                            -> 偏向安全型
```

### 2.3 核心：7 类"关系卡点"诊断（优先级命中制）

每个卡点输出一个结构化对象 `diag = {type, challenge, rootCause, breakthrough, avoid}`，后面所有线上/线下/时机/禁忌策略**全部围绕这一个 diag 展开**。阈值与顺序（源码原文）：

```js
const isAvoidant       = tAvoidance.score > 40;
const isShortReplier   = tStats.avgLength < 8;   // 注意：阶段判定用<6，卡点点用<8
const isIntrovert      = extroversion < 45;
const isExtrovert      = extroversion >= 55;
// 级联顺序 = 优先级，先命中先定调：
if      (isAvoidant)          -> type:'avoidant'        回避型：越追越逃，把"对话"变"留言"
else if (avgLength<6)         -> type:'shortReplier'    惜字如金：别用字数判兴趣，看回复速度/主动发起
else if (sarcasmMark>0)       -> type:'sarcasm'        敷衍信号：立刻停当前话题，换 TA 感兴趣的重启
else if (isIntrovert)         -> type:'introvert'      内敛：用"分享自己"代替"连环提问"
else if (isExtrovert && followUps==0) -> type:'shallowExtrovert'  热闹但不深：追问"那你当时什么感受"
else if (tIntimateEmoji>0)    -> type:'intimate'       已发亲密信号：接暧昧但不急于表白
else                          -> type:'plain'          平稳无记忆点：制造"只有你们懂的梗"
```

每个 diag 四件套（以 avoidant 为例）：
- `challenge`：`${nickname}有回避倾向——越靠近越想逃，你追得紧TA退得快`
- `rootCause`：`回避型的核心恐惧是"被吞噬感"，任何"你必须回应我"的压力都会触发防御`
- `breakthrough`：`把"对话"变成"留言"——你分享，TA接不接都行，消除回复压力后TA反而主动靠近`
- `avoid`：`追问、逼表态、连发消息、用"你怎么不理我"施压`

**分寸门控**（防止对陌生人给暧昧建议）：

```js
const isEarlyStage = /刚认识|陌生人|不久|几天|一周|两周/.test(knownDuration)
                  || /陌生人|刚认识/.test(relationship);
const isIntimateStage = /暧昧|恋爱|情侣|对象|男朋友|女朋友|老公|老婆|伴侣/.test(relationship);
```

### 2.4 它的"诊断"本质

AIta **没有机器学习模型**。所谓"诊断" = 一组**手工统计特征（平均字数、追问数、表情数、主动占比）→ 一组硬编码阈值 → 一棵固定优先级的 if/else 决策树 → 命中一个卡点模板 → 套模板话术**。warmthScore 是唯一的复合分，其余全是单点阈值。输出是面向用户的**解释性散文**，不是可复现的数值分类。

## 三、PsyDI 渐进探测：状态机 / 自适应下一题 / 停止条件 / 画像累积

### 3.1 状态机（`psydi_mini_agent.py` 实读）

```python
class PsyDIMiniAgent:
    def __init__(self):
        self.reward_model = RewardModel()      # 评分模型
        self.prompt = open('prompt.txt').read() # 咨询师 persona
        self.max_turn = 5

    def reset(self):
        self.table = None; self.history = []
        self.history.append({"role":"system","content":self.prompt})
        self.history.append({"role":"assistant","content":"你好！...请告诉我一个具体问题或情境..."})

    def run(self, init_post_list):
        self.init_table(init_post_list)                 # ① 建表
        answer = self.choose_post_to_ask(init_post_list)  # ② 选最纠结的一条动态
        count = 0; description = None
        while count < self.max_turn:                    # ③ 探测主循环
            question = self.get_question(answer)        #    LLM 出下一题
            if re.search(r'自我描述[】:：\t\*]*\s*(.*?)(?=\.|$)', question):
                description = question                  #    ④ 停止信号：LLM 自己喊"我够了"
                break
            count += 1
            answer = input(...)                         #    用户作答
        self.update_table(description or question)      # ⑤ 把整轮 Q&A 合成一段"新动态"回灌评分表
```

### 3.2 评分表怎么建 / 怎么更新（`reward_model_inference.py` 核心算法）

**四个维度先映射成 ±1 向量**：E/I、N/S、F/T、J/P。

```python
self.ei_dict = {'E':1,'I':-1}; self.ns_dict={'N':1,'S':-1}
self.ft_dict = {'F':1,'T':-1}; self.jp_dict={'J':1,'P':-1}
# LlamaForSequenceClassification(num_labels=4) 输出 4 个 logit，对应四个维度
```

**单条动态打分**：模型对"判断该动态用户多大概率是某 MBTI"输出 4 维 logit → 点乘该类型的 ±1 标签向量 → 取均值 → 再用该类型**预先统计好的均值/标准差做正态 CDF 归一化**：

```python
reward = (reward * t_label).mean().item()
mean, std = self.value_stat[mbti]            # 16 个类型的 mean/std 全部硬编码在代码里
reward = norm.cdf(reward, loc=mean, scale=std)
```

**初始化表**：对每条初始动态、对 16 个类型各打一次分，跨动态取均值后线性拉伸到 `[20, 50]`：

```python
type_table[mbti] = np.interp(rewards.mean(), [0,1], [20,50])
```

**更新表（关键：自适应学习率）**——新证据不会等权覆盖旧判断，而是**越确信的类型，权重越小**，防止反复横跳：

```python
def update_function(self, x):   # x = 旧分数(0~100)
    # 分段线性：x=50 → weight=25；x=80 → weight=10；再 clamp 到 [3,60]
    ...
def update_table(self, new_post, type_table):
    for mbti in ...:
        reward = ... # 新动态对该类型的 CDF 概率
        weight = self.update_function(old_reward)
        new_reward = 2 * weight * reward - weight
        type_table[mbti] = min(max(0, old_reward + new_reward), 100)
```

含义：初始模糊（50 分附近）时单次证据可撬动 ~25 的调整；已经很确信（80 分）时单次只动 ~10；天花板 60、地板 3，保证收敛但不锁死。

### 3.3 自适应下一题：专挑"最纠结"的维度追问

```python
def choose_post_to_ask(self, post_list):
    sorted_items = sorted(self.table.items(), key=lambda kv: kv[1], reverse=True)
    top_mbti = [k for k,_ in sorted_items[:2]]     # 当前领先的两个类型
    return self.reward_model.select_post(post_list, self.post_raw_reward, top_mbti)

def select_post(self, post_list, post_raw_reward, top_mbti):
    # 找出 Top-2 两个类型在哪个维度上不同（如 INFP vs ISFJ → [0,1,0,1]）
    diff_index = [1 if top_mbti[0][i]!=top_mbti[1][i] else 0 for i in range(4)]
    # 把候选动态在两个类型下的原始分都排序求和，按"差异维度"加权，
    # 选那条最能在二者分歧维度上拉开差距的动态来追问
    ...rank_list = einsum(...diff_index)...
    return post_list[rank_index.pop()]
```

**探测逻辑一句话**：不问新问题，而是**回看用户已说过的话里，哪一条最能区分当前两个最可能的人格类型，就围绕它追问**。这就是"渐进式、聚焦歧义点"的工程实现。

### 3.4 出题 prompt（`prompt.txt` 实读，可直接借鉴的结构）

- 人设：**MBTI 认知分析咨询师**，精通荣格八维（te/ti/fe/fi/se/si/ne/ni）。
- 约束：一次只问一个问题；选项用 **ABCD 角色扮演第一人称**写（"如果是你，你会怎么做…"），四个选项分别对应不同认知功能，区分度要大；**多轮问题必须递进、不重复**；提问时先 `*猜测潜在动机*` 再 `**过渡到下一个问题**`。
- 停止：**问 2~4 轮就停**，停止后立即按固定格式输出：

```
【你的MBTI是】：INTP
【自我描述】：<把这几轮的题目+用户所选答案，串写成一段连贯的"我是一个怎样的人"的自述，一题不漏>
```

### 3.5 停止条件（双重）

1. **LLM 自发停止**：生成内容里命中正则 `自我描述【:：…】`，说明它认为信息够了，主动转成结论；
2. **硬上限**：`max_turn = 5`（prompt 里写的是 2~4 轮，代码上限 5，留缓冲）。
停止后把整段问答合成一条"新动态"回灌评分表完成画像累积。

## 四、反推：它们分别怎么解决"诊断"和"探测"

- **AIta 解决"诊断"（判定一段关系卡在哪个模式）**：
  它把"关系阶段/卡点"这种模糊判断**工程化为可计算特征**——平均字数、追问次数、亲密表情数、主动发起占比、爱称命中。再用一棵**带优先级的决策树**消歧：先验（爱称/用户自报关系）> 复合分（warmthScore）> 单点阈值（字数/回避分）> 兜底。卡点不是打分排序，而是**首命中分类**，且每个类别绑定一套现成的"根因—突破—禁忌"话术模板。优点是零模型、毫秒级、可解释；缺点是阈值拍脑袋、规则之间重叠靠顺序硬解。

- **PsyDI 解决"探测"（怎么一步步问出人格画像）**：
  它的核心不是"问得更多"，而是**"在信息增益最大的地方问"**。维护一张 16 型概率表，每轮找出 Top-2 最纠结的类型，只在二者**分歧的那个维度**上挑最有区分度的旧发言来追问；更新时用**自适应学习率**（越确信越难被新证据撬动）；停止由"LLM 自己判断信息已足 + 硬轮次上限"双重控制。本质是一个**针对歧义点的主动信息收集（active probing）状态机**，而不是固定问卷。

### 5.1 搬到 `services\analysis_orchestrator.py` / `persona_analyzer.py`

### 5.2 搬到 `services\psydi_probe.py`（已有骨架，补算法）

1. **自适应学习率更新表**（照搬 `update_function` + `update_table`）：
   ```python
   def _probe_weight(old_score: float) -> float:   # 旧分越确信，权重越小
       # x=50→w=25, x=80→w=10, clamp[3,60]，分段线性
   def update_profile_table(new_evidence: str, table: dict) -> dict:
       for k in table:
           w = _probe_weight(table[k])
           delta = 2*w*new_prob[k] - w
           table[k] = min(max(0, table[k]+delta), 100)
   ```
   这正好补现有 `_confidence_of / _unresolved_score` 缺的"累积平滑"——避免每条新证据都把画像推翻重来。

2. **下一题挑歧义点**（升级 `next_best_question`）：不再通用地"找 unresolved 分最高的维度"，而是**先取当前领先的两个画像假设，找出二者分歧的维度，再从已有聊天记录里挑最能区分二者的那条发言来追问**——对应 `choose_post_to_ask + select_post`。

3. **停止条件双闸**：现有 `probe_plan(n=3)` 写死轮数。改成 ①置信度收敛（Top1-Top2 差距超过阈值）或 LLM 输出结论标记就停；②硬上限 `max_turn=5`。

## 六、坏设计 / 避坑（两个项目都有）

**AIta 的坑：**
1. **阈值全是拍脑袋**：`warmthScore>55`、`avgLength<6`、`avoidance>40`、`extroversion<45/55`……没有任何标定/回测依据，换一批聊天样本就失真。搬过来时**阈值必须做成可配置参数，并用 LoveAI 自己的聊天数据标定**，别照抄数字。
2. **决策树"先命中先定"= 任意消歧**：一个人可能既简短又回避，因为 avoidant 排在 shortReplier 前面就永远是回避型。重叠维度应该打分取加权最高，而不是 if/else 顺序。
3. **关键词表脆弱**：`COUPLE_TERMS / SENTIMENT_POSITIVE / INTIMACY_MARKERS` 是硬词表，作者自己就踩过"哈哈我失恋了"误判（哈哈被算正向词，没看是否同时有负面事件词）。中文谐音梗/网络梗必须配"负面事件词同时出现"的互斥规则。
4. **9500 行单文件**：不可维护、不可测试。只搬逻辑，绝不搬工程形态。
5. **输出是模板散文**：同一个卡点每次措辞几乎一样，不可复现、无分数留存。我们要保留结构化 `diag` 对象 + 数值证据，文案另算。

**PsyDI 的坑：**
1. **评分模型是私有重资产**：真正打分靠一个微调的 Llama 序列分类器（`OpenDILabCommunity/PsyDI-RM-v0.1-zh`），没这个模型时 `FakeRewardModel` 直接是 `init 全 0.5、不更新、选第一条`——**mini 版脱离了它的奖励模型就是个空壳状态机**。LoveAI 不要假设能白嫖它的 RM，我们要么用 LLM-as-judge 替代打分，要么自己训。
2. **`value_stat` 的 mean/std 是它自家数据的统计量**：16 个类型的分布参数硬编码死，换人群/换语言就偏移。搬 CDF 归一化思路可以，**那组数不能直接搬**。
3. **停止条件靠正则脆弱匹配 LLM 输出里的"自我描述："**：换模型、换 prompt 措辞就可能永远命不中，最后只能靠 max_turn 兜底。我们要用结构化 JSON 结论字段（如 `{"done":true,"mbti":...}`）替代文本正则。
4. **轮次口径不一致**：prompt 说"问 2~4 轮"，代码 `max_turn=5`，文档宣传"12~15 个问题"——三处对不上。说明连作者自己都没固定探测长度，我们要以"置信度收敛"为准，别照搬任何固定数字。
5. **MBTI 本身科学性存疑**：它的探测对象是 MBTI。LoveAI 要的是依恋/关系模式画像，搬的是"状态机+歧义点选题+自适应权重"这套**方法**，不要把 16 型标签体系一起搬过来。

### 2.2 力参数初始化代码（从 minified bundle 还原的可读结构）

```js
// 还原自 nrd_main.32286.chunk.js @546354 附近
const f = o.forceSimulation();
f.nodes(e);
f.force("center", o.forceCenter(l[0], l[1]));          // 中心化，center 坐标从配置传入

const p = o.forceLink();
p.id(node => node[s]);                                  // link 的 source/target 按 id 字段映射
if (a) {
  if (isFunction(a)) p.distance(edge => a(edge));       // 距离可固定值，也可按边函数返回
  else p.distance(a);
}
f.force("link").links(t);

const E = o.forceManyBody();
if (h !== undefined) E.strength(h);                    // charge 强度（斥力）外部传入
if (r !== undefined) E.distanceMin(r);                 // 斥力生效最小距离
if (n !== undefined) E.distanceMax(n);                  // 斥力生效最大距离
f.force("charge", E);

const b = o.forceCollide();                            // ★ 碰撞力，防节点重叠
if (isFunction(d)) b.radius(node => d(node));
else if (d !== undefined) b.radius(d);
if (c) b.radius(node => node[c] || 10 + d);             // 按节点属性算半径，默认 10+d
f.force("charge2", b);
```

**设计要点（可直接搬）：**
1. **四力组合**：`center`（居中）+ `link`（连接）+ `charge`（斥力）+ `charge2`（collide 碰撞）。碰撞力是它节点不重叠的关键——3d-force-graph 默认不带 collide，要自己加。
2. **所有力参数都从外部 opts 传入**（h=strength, r=distanceMin, n=distanceMax, a=link distance, c=radius key），不在代码里写死。
3. **半径回退值 `10 + d`**：没指定半径的节点给个默认 10 加偏移，避免 NaN 塌陷。

interface RelationNode {
  id: string;            // 唯一 id，如 "person:zhangwei"
  name: string;          // 显示名
  type: 'self' | 'partner' | 'family' | 'friend' | 'colleague' | 'acquaintance';
  val: number;           // 中心度，决定球体积（self/partner 最大，如 10；普通人 1~3）
  color?: string;        // 可选；不给则用 nodeAutoColorBy('type') 自动分组着色

}
interface RelationLink {
  source: string;        // node.id
  target: string;       // node.id
  type: string;          // 关系类型：lover/family/friend/work/conflict
  weight: number;        // 亲密度 0~1，映射到边宽/不透明度
  color?: string;
  label?: string;        // 边 tooltip，如 "交往3年"
}
type GraphData = { nodes: RelationNode[]; links: RelationLink[] };

## 六、坏设计 / 避坑记录

1. **NRD 的"3D"是营销话术，底层是 zrender 2D Canvas**——别被名字误导去花精力逆向它的 WebGL，它根本没有。好处是：它证明了"几百节点关系图用 2D Canvas 也能跑顺"，给了我们性能兜底方案（真 WebGL 卡了就降级到 zrender/Canvas2D 伪 3D）。
2. **3d-force-graph 默认背景 `#000011` 深蓝不透明**——LoveAI 是透明桌宠窗口，必须显式 `backgroundColor('rgba(0,0,0,0)')`，否则一个大黑块。
3. **`enablePointerInteraction=true` 默认开**——鼠标拾取每帧 raycast，节点上千后掉帧明显。节点 >500 时关掉它，或自己节流。
4. **3D 力导向在 ~300 节点后开始掉帧**（WebGL draw call + 物理 tick）。对策：`nodeResolution=4`、`linkWidth=0`（用 Line 不用 Cylinder）、`cooldownTicks=200` 后冻结物理、`warmupTicks` 预跑。NRD 敢用 2D Canvas 就是这个原因。
5. **d3graph 只适合导出静态 HTML**——别指望拿它做实时交互组件，它的产物是一次性快照。
6. **react-force-graph 需要 React 构建链**——LoveAI 没有 npm/webpack，硬上会把整个项目拖进工程化泥潭，不值。
7. **闭源 bundle 反推的不确定性**：NRD 的 Space.View 3D 内部 chunk 未登录拿不到，本文标"推测"的部分不要当确证用；它的力参数是从 minified 代码还原的，变量名已丢失，数值默认值要在我们自己环境里实测微调。
8. **collide 力会让图变"鼓包"**——NRD 用 `10+d` 回退半径是防 NaN，不是最佳；我们按节点 val 算半径更合理，但 radius 太大会把节点顶散，要实测。

## 二、标签体系（taxonomy）

### 2.1 顶层维度 = "层（Layer）"，不是一张扁平表

DSM 的标签不是一次性拍出来的，而是**分层流水线**，每层产出自己的标签族（确证，`pipeline.py` 的 run_* 方法清单）：

| 层 | 干什么 | 产出的标签族 |
|---|---|---|
| L1 linguistic | 语言基础统计 | 词数、句长、词频 |
| L2 semantic/topics | 主题 | 话题分布 |
| **L3 psychological** | 人格/动机/情绪 | **Big Five(OCEAN)、Dark Triad、Schwartz价值观、Moral Foundations、Needs(nAch/nAff/nPow)、Locus of Control、Regulatory Focus、Grit、VADER情绪** |
| **L4 cognitive** | 认知/人际/动力 | **认知偏差(bias)、Beach扭曲、防御机制、人际空间、关系模式、心理动力** |
| L5 narrative | 叙事/元 | 原型(archetypes)、VIA优势、心理灵活性、反思功能、时间取向 |
| L6 therapeutic | 临床向 | 情绪调节、早期适应不良图式(EMS)、认知信任、治疗关系 |
| L7 adaptive/shadow | 整合层 | 阴影侧写、人生脚本、自适应模式、校准、交叉验证 |

> LoveAI 是"关系分析/伴侣画像"，真正对标的是 **L3（人格特质）+ L4（关系模式/人际空间/防御机制）+ L7（交叉验证/校准）**。L5/L6 临床向先不碰。

### 2.2 单个标签的数据结构（确证，`l3_big_five.py`）

这是 DSM 里最完整、最值得直接抄的 Tag schema：

```python
@dataclass
class BigFiveFacet:                       # 二级子特质（facet）
    name: str
    score: float                          # 0-100
    evidence: list[str] = ...             # 最多 10 条原话引用
    marker_count: int = 0

@dataclass
class BigFiveFactor:                      # 一级维度（O/C/E/A/N）
    name: str
    code: str                             # "O"
    score: float                          # 0-100
    facets: dict[str, BigFiveFacet]       # 下挂 facets
    evidence_high: list[str]              # 支持"高分极"的原话
    evidence_low: list[str]               # 支持"低分极"的原话
    total_markers: int = 0
    # to_dict() 里派生：
    #   level: high(>=70)/moderate(>=40)/low
    #   sparse: total_markers < 3
```

落到 DB（确证，`l3_big_five.py:809` 的 `CREATE TABLE`）：
```sql
CREATE TABLE l3_big_five_profile (
  id VARCHAR PRIMARY KEY DEFAULT 'user',
  factors JSON,        # {O:{name,score,level,total_markers}, ...}
  facets JSON,         # {O:{fantasy:{score,marker_count}, ...}}
  evidence JSON,       # {O:{high:[...≤10条], low:[...≤10条]}}
  confidence VARCHAR, # very_low/low/medium/high/very_high
  confidence_score DOUBLE
);
```

### 2.3 标签怎么定义 = 双语正则 marker 集（确证，`lexicons/needs.py`、`l3_big_five.py`）

每个标签 = 一个 **{high: {facet: {en:[...], ru:[...]}}, low: {general:{...}}}** 的正则词表。例（nAch 成就需求，`lexicons/needs.py`）：
```python
NACH_MARKERS = {"en": [r"\b(?:want|wanted) to be the (?:best|first|top)\b",
                       r"\b(?:need|strive|aim) to (?:achieve|win|succeed|excel)\b",
                       ...],
                "ru": [r"\b(?:хочу|хотел[а]?|стремлюсь) быть (?:лучшим|первым)\b", ...]}
```
- **双向极点**：high markers 算"高分极命中数"，low markers 算"低分极命中数"。
- **按语言归一**：命中数 ÷ **同语言** marker 总数（不是除以全部 marker），防止俄语词典大就压过英语（确证 `split_keywords_by_lang` / PRD-149）。

### 2.4 取值与置信度（确证）

**因子分怎么算**（`l3_big_five.py:961-969`）——这是核心算法：
```python
total = high_count + low_count
if total >= 3:
    score = (high_count / total) * 100     # 高/低命中比 → 0~100
else:
    score = 50.0                            # ★ 不足3个marker → 中立50，并标 sparse
```
- facet 分 = `min(100, round(命中数/同语言marker数 *100))`。
- **置信度不是 per-tag 的，而是 per-文案量的全局分带**（`layers/confidence.py`，全项目唯一真源）：

| 词数 word_count | 等级 | 数值 |
|---|---|---|
| <300 | very_low | 0.2 |
| <1000 | low | 0.4 |
| <3000 | medium | 0.6 |
| <10000 | high | 0.8 |
| ≥10000 | very_high | 0.95 |

- **稀疏门**：`total_markers < 3` → `sparse=True`，此时不给 0/100，hold 在 50 中立。这是防"3句话就敢下结论"的关键设计。

### 2.5 年龄/性别常模校正（确证，`engine/norms.py`）

给分数加"和同龄人比"的语境：
```python
norms = BigFiveNorms(age=35, gender='m')
cmp = norms.compare('O', 75)
# → {'norm':62, 'diff':+13, 'percentile':74,
#    'percentile_calibrated': False,          # ★ 永远 False
#    'percentile_kind':'uncalibrated_norm_position',
#    'label':'↗ above', 'text':'...'}
```
- 常模表是 Soto&John(2012)/Weisberg(2011) 的**方向近似手调值**（0-100），不是真人口普查。
- z = (user−norm)/SD(=20) → 正态 CDF → 百分位。
- diff>12 显著高 / >5 偏高 / <-5 偏低 / <-12 显著低。
- **关键诚实设计**：`percentile_calibrated` 永远为 False，并强制下游文案**禁止说"你超过了X%的人"**——因为词典分和问卷常模根本不在一个量纲上。

## 三、侧写引擎流程（抽取 → 证据累积 → 置信度更新 → 报告）

### 3.1 总流程（确证）

```
聊天导出(chatgpt/claude/...)
  → parsers 解析进 DuckDB messages 表(content, role, subject_id, timestamp)
  → mask_non_self_spans(text)   # 先剥掉引语/第三人称转述（防别人的话污染自己画像）
  → L1→L7 各层依次跑，每层把结果写进自己独立的 DuckDB 表
  → exporters 汇总成 HTML / DOCX / FULL_PROFILE.md
```
- **只分析 `role='user'`** 的消息（确证 `_fetch_user_text` / `analyze_from_db`）——AI 说的话不计入"你"。
- 预飞行：空 DB 直接 raise，不会给你一张全绿但没数据的报告（`run_full_analysis` preflight）。

### 3.2 证据怎么挂到标签上（确证，`_negation.py`）

核心函数 `negation_aware_find()`：
```python
for m in pattern.finditer(text):
    boundary = max(prefix.rfind('.'), rfind('!'), rfind('?'), rfind('\n'), rfind(';'))
    if not _negated(tokens, idx, window=3, boundary):  # 前3个token内是否定词，且不跨句
        kept.append(m)
# 证据 = 命中位置前后各截50字符，加 "..."
snippet = text[max(0,m.start()-50) : m.end()+50]
```
- **否定窗=前3个token，且不能跨句**（"我不焦虑。我很焦虑"不会被否定吞掉第二句）。
- **否定词表**中英双语合并（`NEGATION_WORDS`：not/n't/never.../не/нет/никогда...）。
- **自/他者遮蔽**（`mask_non_self_spans`）：引语 `«"..."»` 和第三人称转述 `he said that...` / `он сказал, что...` 整段替换成空格——别人说的话绝不进你的画像。
- 每个标签最多挂 **10 条原话**（`evidence[:10]`），前后 high/low 各一份。

### 3.3 两阶段"候选 → 裁决"（确证，偏差类标签专用：`l4_bias_spans.py` + `l4_adjudicate.py`）

对**高假阳性**标签（认知偏差），DSM 不直接信词典，而是：

**阶段1 便宜规则过滤**（`detect_bias_spans` + `apply_context_filters`）：
```python
# 命中即生成候选：
{candidate_id: uuid, bias_type, marker, start, end, span_text,
 context_before(120字), context_after(120字), speaker_role}
# 然后跑上下文过滤器，直接给 decision：
- speaker 是 assistant/ai/bot          → drop (conf 0.95)   # AI说的不算
- 前40字有否定词                        → 标记 negation
- 在引号内 / "you said" / 习语(idiom)   → drop
- 高FP类型(confirmation_bias等)        → uncertain (0.45)   # 升级给LLM
- 否则                                  → keep (0.75)
```

**阶段2 LLM 裁决**（`BiasAdjudicator`，只对 uncertain/需复核的候选）：
- system prompt 锁死边界："只许 keep/drop/uncertain，**不许发明新 bias_type，不许下诊断，不许给治疗建议**，只回一个 JSON"。
- 输出 schema：`{candidate_id, bias_type, decision, confidence:0-1, reason_codes[], reason_short:≤120字}`。
- **fail-closed**：解析失败/超时/被 fence 拦截 → **一律 drop**，绝不 auto-keep（`parse_bias_verdict` 返回 None 即 drop）。
- **预算闸门**（`adjudicate_budget_for_corpus`）：≤500条消息最多40次LLM调用/180s；≤2000条→80次/360s；更多→120次/480s。
- provider 白名单：默认只允许本地 LM（Ollama/LM Studio/loopback），公网 API 必须显式 `allow_api_adjudicate`。

### 3.4 置信度更新 / 规则 vs AI 融合（确证，`engine/blend.py`）

`--blend` 模式做"现实校验对照"，**非破坏性**：
- 规范分 `factors[X].score` 永远保留**规则值**（可复现基线不动）。
- LLM 对同一文本另打一套分，存进 `_blend` 块：
```python
contrast[key] = {"rule": 75, "ai": 62.0, "delta": -13.0, "agreement": "low"}
# agreement: |delta|<=8 high; <=20 medium; 否则 low
```
- 多源加权合并 `_weighted_merge`：按"该 key 谁给过分"做归一化加权平均（rule/local/api 权重来自 `PrecisionConfig`）。
- 设计哲学（原文）：**"规则说你语言里可测地表现出的" vs "AI 推测的"之间的 gap 才是洞察点**，不是把两者平均成一个数糊你脸上。

### 3.5 报告渲染（确证，`src/exporters/`）

- 多格式：`full_profile_html.py`(HTML) / `docx_profile.py`(Word) / `summary_profile.py` / `report_schema.py`(机器可读 JSON schema)。
- 样例：`docs/examples/example-profile-en.html` —— 顶部 confidence badge 写 "Scores compared to age 34 · female norms"，每个维度配 evidence 引用列表。
- 报告里**强制带校准披露**（README 提到 v0.6.2 加了 "relative Schwartz scale + saturation disclosures"）——即"以下是相对位置，不是确诊"。

### 4.3 可抄的抽取/裁决 prompt 写法（落到 engine/prompts 层）

裁决类 prompt 的**边界锁**值得原样借鉴（`l4_adjudicate.py:65`）：
> "You adjudicate *candidates*. You may **ONLY** decide keep/drop/uncertain for the given candidate_id and type. **Never invent a new type. Never diagnose. Never give therapy advice.** Reply with a single JSON object only."

要点：① 只许三值决策；② 不许发明新标签；③ 不许诊断/建议；④ 强制 JSON。LoveAI 做"关系卡点诊断"时照这个写，能防 LLM 自由发挥瞎贴标签。

### 4.4 标签维度建议（LoveAI 关系场景精简版）

不必搬 400 指标，先这几族（都在 DSM 里有现成词表思路）：
- **关系模式**（对标 `l4_relationship_patterns.py` / `relationship_patterns.py` 词典）：依恋类型、追逃、指责-讨好。
- **防御机制**（对标 `defense_mechanisms.py`）：否认/投射/合理化。
- **动机三需**（对标 `lexicons/needs.py`）：nAch 成就 / nAff 亲和 / nPow 权力——关系里"要控制 vs 要亲密"直接用。
- **Big Five 精简版**：只要 O/C/E/A/N 五个 factor + evidence，不要全 facet。

## 五、坏设计 / 避坑（它自己都承认的短板）

1. **置信度是"文案量"不是"证据质量"**（确证 `confidence.py`）：1万字就 very_high=0.95，但这1万字全是车轱辘话也照样 0.95。**它没有按"标签独立证据条数/跨情境一致性"加权置信度**——LoveAI 应补：置信度 = f(词数分带, 独立证据条数, 跨对话一致性)，别只看字数。
2. **词典打分本质是词频LIWC，效度存疑**（它自己 `norms.py` docstring 都写了：词典分 vs 问卷常模不同量纲，百分位未校准）。别信"算法测出来你的人格"，只当"你语言里频繁出现的模式"。
3. **LLM 只在 maximum 模式调，且非确定性**（`blend.py`）：同一段文本两次跑 AI 分会不一样，所以它把规范分锁死成规则值。**LoveAI 若做在线增量累积，千万别拿 LLM 分直接覆盖历史分**——会漂移。
4. **AGPL 传染性**：见第一节，别抄字面代码。
5. **多语言归一靠字符占比**（`split_keywords_by_lang`：混语≥25%两种都跑），中文场景得重写——它只有 en/ru，**没有中文词典**，LoveAI 的中文 marker 要自己造。
6. **稀疏阈值是拍的**（<3 marker 中立、词数分带阈值）——它自己标注是 hand-tuned，LoveAI 可参考但要用自己语料重标定。
7. **fail-closed 有代价**：解析失败全 drop，会漏真阳性（真偏差被当噪声丢了）。关系场景里"漏报卡点"比"误报"代价高，需权衡。

## 六、优先级初判（P0/P1/P2）

## 难度怎么打分为真

### 1. UncommonRoute：三级级联（cascade）分类器

PyPI 文档里给的架构图（确证）：

```
Input Prompt
 │
 ▼
┌─────────────────────┐
│ 1. Trivial Override │ greeting / empty / very long → 即时决策，不进模型
└─────────┬───────────┘
 │
 ▼
┌─────────────────────┐
│ 2. Learned Model    │ Averaged Perceptron on 39 features（avg 356µs）
│   12 structural      │ + 15 unicode + 12 keyword
└─────────┬───────────┘
 │
 ▼
┌─────────────────────┐
│ 3. Rule Fallback    │ 训练好的权重不可用时，用手调权重兜底
└─────────┬───────────┘
 │
 ▼
 Tier + Model + Cost
```

**关键设计点**：先过 trivial override 砍掉「根本不用动脑」的请求（空文本、纯问候、超长），剩下的才进 39 特征感知机。这就是它能做到 0.5ms 的原因——大多数请求在第 1 层就分流了，根本不跑特征工程。

### 2. 39 个特征（全部列名，确证自 PyPI）

**Structural（12 个）：**
`normalized_length, enumeration_density, sentence_count, code_markers, math_symbols, nesting_depth, vocabulary_diversity, avg_word_length, alphabetic_ratio, functional_intent, unique_concept_density, requirement_phrases`

**Unicode（15 个）：**
`basic_latin, latin_ext, cyrillic, arabic, devanagari, thai, hangul_jamo, cjk_unified, hiragana, katakana, hangul_syllables, punctuation, digits, symbols_math, ...`

> 这组特征的真实用途不是「识别语言」，而是**间接判断任务类型**：CJK + 高 requirement_phrases 密度 = 中文多需求诉求；code_markers + math_symbols 高 = 代码/数学；enumeration_density 高 = 「帮我列 5 点」这种结构化请求。中文场景下 cjk_unified 是必加特征。

**Keyword（12 个）：**
`code_presence, reasoning_markers, technical_terms, creative_markers, simple_indicators, imperative_verbs, constraint_count, output_format, domain_specificity, agentic_task, analytical_verbs, multi_step_patterns`

> 注意：它**不是**我们现在 `difficulty_router.py` 那种「命中关键词就判 hard」的硬规则。关键词在这里被压成 12 个**聚合二值/计数特征**（例如 `reasoning_markers` 是「出现几处推理连接词」的计数，不是单个词），再喂给感知机做加权。这是它比纯关键词准得多的原因。

### 4. 对照：RouteLLM 走的是另一条路（真实源码 routers.py 已读）

RouteLLM **不判抽象难度**，它判「strong 模型赢 weak 模型的概率」。核心抽象（确证源码）：

```python
class Router(abc.ABC):
    # 返回 0~1，表示 strong 模型的胜率
    @abc.abstractmethod
    def calculate_strong_win_rate(self, prompt): ...

    def route(self, prompt, threshold, routed_pair):
        if self.calculate_strong_win_rate(prompt) >= threshold:
            return routed_pair.strong
        else:
            return routed_pair.weak
```

它内置 5 种路由器（确证源码）：

| 类 | 怎么打分 | 开销 |
|---|---|---|
| `RandomRouter` | 随机 0~1 | 基线 |
| `MatrixFactorizationRouter` | MFModel.pred_win_rate(strong_id, weak_id, prompt)，向量内积 | 轻 |
| `CausalLLMRouter` | 微调 Llama-3-8B，5 个 special token `[[1]]..[[5]]` 输出等级，`score_threshold=4` | 重（要起 8B 模型） |
| `BERTRouter` | BERT 三分类，softmax 后取 label1+label2 概率作为「强模型赢」 | 中 |
| `SWRankingRouter` | 用 text-embedding-3-small 算 prompt embedding，跟 Arena 历史 embedding 算相似度，再加权 Elo 胜率 | 中（要调 OpenAI embedding） |

**RouteLLM 的阈值不是「难度分」，是「成本-质量 cutoff」**：例如 `router-mf-0.11593` 意思是「强模型胜率 ≥ 0.116 才走 GPT-4，否则 GPT-3.5」。这个数字是在 MT-Bench 上扫出来的——你愿意为多少质量付多少钱。

### 5. 两条路线对我们的启示（结论）

- **UncommonRoute 路线**（规则 + 轻量感知机）：适合我们——本地、0.5ms、可解释、能用自己的中文对话数据重训。
- **RouteLLM 路线**（ML 偏好分类）：要标注「哪段对话该用强模型」，我们没有这个标注数据，**现阶段不搬**，但它的「二元胜率 + cutoff」抽象值得抄——这比我们现在写死「hard 就走强模型」更灵活。

## 降级 / 兜底 / 反馈闭环

### UncommonRoute 的完整兜底链（确证）

1. **分类器级兜底**：trivial override → 感知机 → 手调规则权重（model 不可用时）。
2. **模型级 fallback chain**：每档有显式 fallback 列表，上游 reject 一个模型自动试下一个。
3. **能力过滤**：请求带 `tools` 或图片时，先把「不支持 tool calling / 多模态」的模型从候选里踢掉，再按 profile 排序，不是单纯按价格排。
4. **Session 状态机**（这是最值得抄的一段）：
   - 默认「每次请求重新分类」；
   - 可选「**只升不降**」：分类器说 COMPLEX 但 session 是 MEDIUM → 升级；分类器说 SIMPLE 但 session 是 MEDIUM → **保持 MEDIUM 不降级**（避免任务中途抖动）；
   - 例外：tool-result 步骤绕过 session hold，直接用分类器建议；
   - **30 分钟无活动 session 自动过期**；
   - **三次相同请求 → 自动升到下一档**（"three-strike escalation"，tool-result 步骤跳过）。
5. **Bandit 选择器**：每档内部不是写死主模型，而是按 profile 权重 + 预测 token 成本 + 观测延迟/吞吐 + 观测可靠性 + 用户反馈 + cache 亲和度 + BYOK 偏好，加一个**有界探索 bonus**，低采样候选会被试探。探索按 `profile + tier` 分桶，保证 SIMPLE/MEDIUM 敢试，REASONING 不乱动。
6. **反馈闭环**：`POST /v1/feedback` 在线学习；`/v1/selector` 能看每个候选的实时打分。
7. **Spend control**：per_request / hourly / daily / session 四档限额，超限返回 HTTP 429 + `reset_in_seconds`。
8. **硬钉模式**：`--mode hard-pin` 把某档钉死在主模型上，只有上游报错才 fallback；默认 `adaptive` 用 bandit。

### 我们自己已有的兜底（free_model_router.py 确证）

我们其实**已经有一套相当成熟的状态机**，只是没跟难度档连起来：

| 机制 | 我们的实现 | 参数 |
|---|---|---|
| 429 限流 | 同模型指数退避 | 1s → 2s → 4s，最多 3 次 |
| 5xx 熔断 | 连续失败翻倍冷却 | 30s 起步，封顶 5min |

### 搬 1：把「硬关键词命中」改成「聚合计数特征」（改 difficulty_router.py）

**现状问题**：`hit_hard = [kw for kw in self.hard_keywords if kw in t]`，命中一个就 hard。
**搬法**：照 UncommonRoute 的 keyword 族，把单个词变成 12 个左右的计数/二值特征：

```python
# 新增 services/difficulty_features.py（或直接塞进 difficulty_router.py）
def extract_features(text: str) -> dict:
    t = text or ""
    return {
        "normalized_length": len(t) / 500.0,          # 截断归一
        "sentence_count": t.count("。") + t.count(".") + t.count("！") + t.count("?"),
        "code_markers": sum(t.count(x) for x in ("```", "def ", "import ", "{", "=")),
        "math_symbols": sum(t.count(x) for x in ("+", "-", "*", "/", "=", "∑", "∫")),
        "enumeration_density": sum(t.count(x) for x in ("1.", "2.", "3.", "、", "（1）")),
        "cjk_ratio": sum(1 for c in t if '一' <= c <= '龥') / max(1, len(t)),
        "reasoning_markers": sum(t.count(x) for x in ("为什么", "凭什么", "怎么", "难道", "其实", "本质")),
        "analytical_verbs": sum(t.count(x) for x in ("分析", "预测", "判断", "推导", "评估")),
        "imperative_verbs": sum(t.count(x) for x in ("帮我", "给我", "写一份", "列一下")),
        "constraint_count": sum(t.count(x) for x in ("不要", "必须", "一定", "但是", "不过")),
        "creative_markers": sum(t.count(x) for x in ("安慰", "夸", "哄", "撒娇", "情话")),
        "agentic_task": int(any(k in t for k in ("侧写", "六维", "数字分身", "博弈"))),
    }
```

然后 `DifficultyRouter._rule` 里不再是「命中 hard 词就 hard」，而是给这些特征加权求和（先用手调权重，跑一段时间再换成感知机）。

### 搬 2：预留的 classifier 接口真接上感知机（改 difficulty_router.py）

我们已经留了 `classifier: Optional[Callable[[str], Optional[str]]]` 注入点（第 68、110 行），**这个架构抄对了**。下一步：

```python
# 新增 services/perceptron_classifier.py
# 用 sklearn.linear_model.Perceptron(warm_start=True) 即可，模型文件存 config 目录
class PerceptronDifficultyClassifier:
    def __init__(self, model_path: str):
        self.clf = joblib.load(model_path) if exists else None
    def __call__(self, text: str):
        if self.clf is None:
            return None  # 回落规则
        x = np.array([list(extract_features(text).values())]).reshape(1, -1)

### 搬 4：抄 Session「只升不降 + 三次相同请求升级」（新建 services/difficulty_session.py）

这是 UncommonRoute 最值钱的一段逻辑，直接搬：

```python
# 新建 services/difficulty_session.py
SESSION_TTL_SEC = 1800          # 30 分钟
THREE_STRIKE_N = 3              # 三次相同请求升级

class DifficultySession:
    def __init__(self):
        self._state: dict[str, dict] = {}   # session_id -> {"tier":..., "last":..., "same_count":..., "last_sig":...}

    def decide(self, session_id: str, prompt_sig: str, classifier_tier: str) -> str:
        now = time.time()
        st = self._state.get(session_id)
        if st and now - st["last"] > SESSION_TTL_SEC:
            st = None
        if st is None:
            tier = classifier_tier
        else:
            # 只升不降
            order = ["easy", "medium", "hard"]
            if order.index(classifier_tier) > order.index(st["tier"]):
                tier = classifier_tier          # 升级
            else:
                tier = st["tier"]               # 不降级
            # 三次相同请求升级
            if prompt_sig == st["last_sig"]:
                st["same_count"] += 1
                if st["same_count"] >= THREE_STRIKE_N and tier != "hard":
                    tier = order[order.index(tier) + 1]
            else:
                st["same_count"] = 1
        self._state[session_id] = {"tier": tier, "last": now,
                                   "same_count": st["same_count"] if st else 1,
                                   "last_sig": prompt_sig}
        return tier
```

**为什么重要**：我们现在每条消息独立判档，同一段对话里用户先聊两句 easy、突然甩一个长问题判 hard、下一句又回到 easy——模型来回切，既贵又跳戏。这个状态机直接解决。

### 搬 5：把「档位 → 模型」做成可配置表 + fallback 链（改 llm_gateway.py）

现在我们的 `difficulty_router.py` 只输出 tier，**没有定义「tier 对应哪个模型」**。照 UncommonRoute 的表，在 config 里加：

```json
{
  "llm.tier_models": {
    "easy":   {"primary": "free-ollama-qwen2.5:7b", "fallback": ["openrouter:free", "gemini-flash-lite"]},
    "medium": {"primary": "kimi-k2.5",              "fallback": ["deepseek-chat", "gemini-flash-lite"]},
    "hard":   {"primary": "gemini-3.1-pro",          "fallback": ["claude-sonnet", "gpt-4o"]}
  }
}
```

然后网关在拿到 tier 后，先试 primary，失败沿 fallback 链走——**这个 fallback 机制我们 free_model_router.py 已经写好了**（429 退避 / 5xx 熔断 / 401 永久禁用），直接复用，不要重写。

### 搬 6：Spend control（新建 services/spend_control.py）

UncommonRoute 的 per_request / hourly / daily / session 四档限额，我们现在没有。对个体户自己用其实不急需，但如果以后要给别人用，**这个是防账单爆炸的最后一道闸**。P2。

## 坏设计 / 避坑

好的坏的都记下来：

1. **UncommonRoute 的 MEDIUM 档才是战场**——它官方原话"most routers can tell cheap from expensive. The money is won or lost in the middle." 我们如果只做「easy vs hard」二分类，会把大量该走便宜模型的请求错判给 hard。**不要做二分类，至少 3 档，且 MEDIUM 档要有足够多的训练样本。**

2. **规则驱动的坑（我们自己 now 在踩）**：把业务词（侧写/NPD/挽回）当难度词用。用户说「我妈昨晚给我打电话又开始念我了」——没有 hard 词，但其实是个需要共情的中等问题；用户说「帮我分析一下他为什么 NPD」——命中 NPD，但其实一句话就能答。**难度特征和任务类型特征要分开两组，不要混在一个列表里。**

3. **RouteLLM 式 ML 分类的坑**：需要「strong vs weak」偏好标注数据，我们没有。直接上 BERT/8B 微调是过度工程——ai-tldr 那篇评测原话："Many teams spend weeks building sophisticated classifiers and discover a five-rule heuristic would have done the job." **先规则，再感知机，最后才考虑微调。**

4. **UncommonRoute 的 bandit 选择器对我们是过度设计**——它要跨十几个模型按成本/延迟/可靠性在线学习。我们候选模型就三五个，写死 fallback 链比 bandit 更可控。**P2，不搬。**

5. **只升不降 session 的坑**：如果用户在 session 中段从「深度分析」切回「随便聊聊」，session 会把后续闲聊也钉在 hard 档多烧钱。**30 分钟 TTL 必须严格执行，且要在前端/日志里能看到「当前 session 钉在 hard 档」，给用户一个手动 reset 的入口。**

6. **三次相同请求升级的坑**：如果用户在反复发同一句话（比如网络卡了重发），会被误判成「这个问题答不好，升级」。**要先判断「上一次是不是失败了」再触发 three-strike，不要把网络重试算进去。**

7. **超长文本当 trivial 处理的坑**：UncommonRoute 把 very long 直接当 override——但我们的场景里，用户粘一大段聊天记录过来恰恰是**最需要强模型**的（侧写/分析）。**不要抄它的 very-long override 方向，我们的 very-long 应该往 hard 走，不是 SIMPLE。**
